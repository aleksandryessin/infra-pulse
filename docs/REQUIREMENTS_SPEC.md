## Обязательность, приоритет и доказательства

`MUST` — условие полной приёмки; `SHOULD` — улучшение после основного сценария;
`OUT` — исключено из текущего scope. P0 — критический путь/инварианты;
P1 — обязательный остаток до сдачи; P2 — расширения. **MUST/P1 тоже блокирует
заявление о полном соответствии**. Сокращение сроков не меняет MUST на SHOULD.

Статус описывает реализацию: `planned` — ещё предстоит; `partial` — есть часть;
`fixture` — сценарий только на synthetic; `implemented` — критерий закрыт
применимым evidence; `waived` — есть явно принятая уступка с областью действия.
Незакрытое решение указывается через D-ID и блокирует соответствующий gate,
но не всю независимую работу. OUT не является статусом готовности.

В таблицах `—` означает, что evidence закрытия отсутствует. Коды E ниже дают
исходное evidence, а не автоматически подтверждают всю строку. Начальные статусы
перенесены из review 21.09 и сверены с деревом/scaffold; новых запусков продукта,
EDA или обучения при формализации не было. При реализации автор обновляет строку

## Маршрут приёмки и выбор среза

1. G-DATA: P-01/M-01 — принят Parquet, accounting/provenance, сравнительный audit.
   Принимает Tech Lead, evidence готовит DS-инженер.
2. G-SLICE: D01 — Tech Lead и DS-инженер выбирают когорту/сценарий по данным;
   frontend-разработчик согласует API/UI. Фиксируются периоды, входы, роль, действие, no-data/no-go
   маршрут, критерии и ID требований. Data gate не гарантирует пригодности ML.
3. G-MODEL: M-02/M-03 — frozen protocol до обучения, сравнительный run и отдельное
   решение о допуске. При no-go можно показать очередь по правилам, сохранив ML-gap.
4. G-ENGINEERING: P-02–P-04/U-02–U-03 — БД/API/UI, сохранность, audit, idempotency,
   права. До G-SLICE допустимы универсальные synthetic проверки этих инвариантов.
5. G-RELEASE: P-05/ALL-01 — объединённый replay, чистый Linux, SLA/20 users,
   restore/rollback и комплект сдачи; решение принимает Tech Lead по evidence команды.

Кандидат G-ENGINEERING/G-SLICE (ещё не утверждённый data-backed demo):
список тревог → карточка объекта → прогноз и объяснения → решение диспетчера →
решение+audit → reload → прогноз и решение сохранены → идемпотентный retry →
scope роли проверен. Наличие прогноза зависит от model gate; карточка наблюдения
или проблемы данных не требует фиктивного risk. История, audit, retry и scope
обязательны при любом выбранном сценарии.

## Изменения, исключения и передача

ID стабильны и не переиспользуются. Изменение смысла/границ требует новой версии
этой базы, записи основания и согласованной правки профильной спецификации/config/контракта.
Обновление evidence без изменения требования получает запись даты/версии кода.
Ответственный за базу — Tech Lead; DS-семантика проверяется обоими DS, UI/API —
владельцами затронутых компонентов. Команда не утверждает решения от имени заказчика.

Каждый PR/передача перечисляет requirement ID, проверку, фактический результат,
статус и оставшиеся D/EX. В README компонента находятся ссылки на его раздел,
без копирования норм. Проверку трассировки выполняет ревьюер по
[CONTRIBUTING](../CONTRIBUTING.md); автоматического CI gate полноты требований пока нет.

Исключение оформляется в [реестре](REQUIREMENTS_DECISIONS.md): EX-ID, requirement ID,
исходная норма, источник разрешения/причина, границы и срок, риск, замена, владелец,
кто/когда принял и когда пересмотреть. До принятия статус требования не `waived`.
Внутреннее принятие ограничения позволяет честно передать частичный результат,
но **не подтверждает соответствие внешнему ТЗ**. Ослабление внешней нормы требует
проверяемого ответа организатора/заказчика; при его отсутствии gap остаётся в сдаче.

Датированные review сохраняют вывод на момент проверки. Исправление отражается
здесь и в STATUS при изменении готовности; следующий review оценивает новую версию.
Новая документация сама по себе не повышает готовность продукта.
