# Подключение данных заказчика: CSV, XLSX и API

Инструкция для администратора сервиса и для разработчиков системы-источника
(SCADA, АСУ ОДС или промежуточная выгрузка), которые передают журнал событий
датчиков в InfraPulse MSK. Требования: ТЗ §7 (интеграция по API), §9 (обработка
не дольше 5 мин), §10 (к системам заказчика — только чтение); в
[нормативной базе](REQUIREMENTS_SPEC.md) — DATA-02, DATA-03, DATA-04, DATA-06,
API-04, SEC-03, OPS-01.

## Два этапа подключения

| Этап | Что передаётся | Как | Кто |
| --- | --- | --- | --- |
| До запуска потока | Справочники, история журнала за прошедшие сутки и месяцы | Файлы CSV или XLSX через раздел «Загрузка» в интерфейсе или `POST /api/v1/imports` | Администратор сервиса (роль `admin`) |
| После запуска | Новые записи журнала по мере появления | Пачки JSON или XML `POST /api/v1/observations` с токеном интеграции | Система-источник |

Оба пути сходятся в одной таблице наблюдений и в одной очереди worker. Ключ
совпадения записи одинаков: канал, время, `ид_события` и значение. Поэтому запись,
пришедшая и в файле, и в пачке, сохраняется один раз. Историю можно догрузить файлом
и после запуска потока: перекрытие не создаёт дублей.

### До запуска: история CSV или XLSX

1. Сначала справочник каналов (`справочник_каналов_датчиков.csv`,
   `format=reference_channels_csv`, [столбцы](#справочник-каналов)). Журнал и пачка без
   справочника получают `failed/reference_missing`. Справочники объектов
   (`reference_objects_csv`) и состояний (`reference_states_csv`) необязательны: без
   справочника объектов на экранах вместо названия объекта — его ID.
2. Затем файлы журнала по суткам (`format=journal_csv`, до 50 MB на файл). Допустимы два
   заголовка: как у [выгрузки организаторов](#журнал-выгрузка-организаторов) и как в
   [Приложении 1 ТЗ](#журнал-приложение-1-тз). В формате Приложения 1 нет признака
   тревожности: он хранится как «не передан», а не как `false`.
3. XLSX принимается с теми же `format` и столбцами: читается первый лист, ячейки
   переводятся в тот же текст, что в CSV. Контейнер определяется по содержимому файла.
4. Результат каждого файла — в разделе «Загрузка» или `GET /api/v1/imports/{id}`:
   принято, дубли, quarantine с номерами строк, неизвестные каналы, заметки о формате
   (заметки — только в ответе API).

```sh
# Туннельный стенд (INFRA_AUTH_MODE=dev_stub). На публичном стенде загрузка идёт через
# интерфейс под учётной записью с ролью admin. Записи журнала — не позже данных стенда
# (раздел «После запуска», п. 4).
curl -F format=reference_channels_csv -F file=@справочник_каналов_датчиков.csv \
  http://127.0.0.1:8000/api/v1/imports
curl -F format=journal_csv -F file=@journal-<сутки>.csv http://127.0.0.1:8000/api/v1/imports
```

Локально, на своём Compose, — тот же запрос с файлами из [`docs/examples/`](#синтетические-примеры)
([сквозная проверка](#сквозная-проверка-за-5-минут)).

Правила разбора CSV — [backend/README](../backend/README.md#загрузка-csv-и-ingestion-worker-b1),
XLSX и Приложения 1 ТЗ — [там же](../backend/README.md#xlsx-журнал-приложения-1-тз-audit-запросов-и-исследование-g1-27092026).
Папки-«почтового ящика» для CSV нет. Прежний `received-watcher` читает JSON другого
формата и устарел; для новых подключений он не используется.

### Форматы файлов

Общие правила для справочников и журнала.

- **CSV:** UTF-8, с BOM или без; разделитель — запятая (у Приложения 1 ТЗ — запятая или
  точка с запятой); ячейки можно брать в кавычки `"…"`, внутри кавычек допустимы запятые и
  переводы строки. **XLSX:** первый лист, те же столбцы.
- **Заголовок** — первая строка, столбцы в указанном порядке, имена ровно такие, без
  лишних и пропущенных столбцов. Нестрого (регистр, `_` или пробел, `ё`/`е`) сравнивается
  только заголовок Приложения 1 ТЗ. Другой заголовок или неверно указанный `format` —
  весь файл `failed` с `error_code=bad_header`; какие столбцы ожидались, отчёт не
  называет — они перечислены ниже.
- **Значения** хранятся как текст, дословно: ID `0012` остаётся `0012`, `1,5` — текстом.
  Число (`value_numeric`) получается только из десятичной записи с точкой (`28`, `0.01`).
  Все ID — строки, диапазон и вид не проверяются.
- **Строка с ошибкой** уходит в карантин с номером строки и причиной, остальные строки
  файла принимаются. Причины: `bad_column_count` (число ячеек не равно числу столбцов
  заголовка), `bad_encoding` (не UTF-8 или символ NUL), `value_too_long` (ячейка длиннее
  4 096 символов), `empty_channel`, `bad_date`, `bad_time`, `bad_bool`,
  `channel_type_conflict` (только Приложение 1 ТЗ). Если ни одной годной строки нет, файл
  `failed/no_valid_rows`. Повтор записи — дубль, а не ошибка: у справочника — та же строка,
  у журнала — тот же [ключ совпадения](#формат-пачки) (канал, время, ИД события, значение).
- **Справочник заменяется целиком.** Каждая загрузка справочника того же вида становится
  действующей версией: канал, которого нет в новой версии, в следующих журналах и пачках
  становится неизвестным. Уже сохранённые записи не переписываются.

#### Справочник каналов

`format=reference_channels_csv`. Один канал — одна строка. Канал, записанный дважды с
разным объектом, типом датчика или типом системы, неоднозначен: его записи сохраняются без
объекта.

```text
ид_канала_данных,тип_инж_системы,тип_датчика,тег_инженерной_системы,название_датчика,ид_объект
demo-700002,Электроснабжение,Состояние фазы,ДЕМО-1.2.,ФВ1 ПК12 (В1),demo-obj-1
```

| Столбец | Значение | Правило |
| --- | --- | --- |
| `ид_канала_данных` | обязательно, текст | Ключ связи с журналом и пачками. Пустое — `empty_channel` |
| `тип_инж_системы` | может быть пустым, текст | Показывается в интерфейсе и Grafana |
| `тип_датчика` | может быть пустым, текст | Прогноз строится только по каналам с типом ровно `Состояние фазы`. Остальные типы принимаются и видны в сообщениях; колокольчик отбирает записи по точному типу и тексту (`Датчик дыма` + `Обнаружен дым`, `Газовый датчик` + `Обнаружен газ` …) |
| `тег_инженерной_системы` | может быть пустым, текст | Хранится как есть |
| `название_датчика` | может быть пустым, текст | Для каналов фазы из названия читаются пикет (`ПК12`, `ПК35-37`) и вид линии: `ГРО`, `РО`, `ФРО`, `ФАО` — освещение, `ФВ` — вентиляция, `ФАНС` — насосы, `ОЗК`; `Ввод`, `АВР`, `ЩАП`, `Межсекционный` — ориентиры схемы. Без пикета линия попадает в столбец «ПК ?» |
| `ид_объект` | может быть пустым, текст | Объект канала. Пустое — записи канала сохраняются без объекта и в прогноз объекта не входят |

#### Справочник объектов

`format=reference_objects_csv`. Если объект записан дважды, на экранах берётся первая строка.

```text
ид_объект,иерархия_уровень,родитель,вид_объекта,диспетчерское_название_объекта
demo-obj-1,3,demo-root,ДУ,Синт. объект 1
```

| Столбец | Значение | Правило |
| --- | --- | --- |
| `ид_объект` | текст | Тот же ID, что в справочнике каналов |
| `иерархия_уровень`, `родитель`, `вид_объекта` | могут быть пустыми, текст | Хранятся как есть, видны в Grafana; прогноз их не использует |
| `диспетчерское_название_объекта` | может быть пустым, текст | Название на экранах. В «Сейчас» и колокольчике — сразу, в «Прогнозе», «Схеме» и «Журнале» — со следующего пересчёта прогноза (загрузки журнала или пачки) |

#### Справочник состояний

`format=reference_states_csv`. Словарь текстовых состояний по типу датчика; с каналом не
связан.

```text
тип_датчика,ид_набор_состояний,название_состояния,тревожное
Состояние фазы,demo-set-1,Неисправен,true
```

| Столбец | Значение | Правило |
| --- | --- | --- |
| `тип_датчика` | текст | Как в справочнике каналов |
| `ид_набор_состояний` | текст | Хранится как есть |
| `название_состояния` | текст | Текст значения, как в журнале |
| `тревожное` | обязательно | `t`, `true`, `f` или `false`; иначе `bad_bool` |

Справочник состояний используется только в Grafana (сводка состояний по типам). Прогноз,
колокольчик и признак `alarm` записей от него не зависят.

#### Журнал: выгрузка организаторов

`format=journal_csv`, заголовок сравнивается строго, разделитель — запятая.

```text
ид_события,ид_канала_данных,дата,время,тревожное,значение_датчика
8000025,demo-700004,2026-06-29,03:10:05,true,Неисправен
```

| Столбец | Значение | Правило |
| --- | --- | --- |
| `ид_события` | может быть пустым, текст | Хранится как текст, уникальным не считается |
| `ид_канала_данных` | обязательно, текст | Канал из справочника. Неизвестный канал принимается без объекта и считается в `unknown_channels`. Пустое — `empty_channel` |
| `дата` | обязательно | `ГГГГ-ММ-ДД`, существующая дата; иначе `bad_date` |
| `время` | обязательно | `ЧЧ:ММ:СС` или `ЧЧ:ММ:СС.ffffff`; иначе `bad_time`. Дата и время — московское время UTC+03:00 |
| `тревожное` | обязательно | `t`, `true`, `f` или `false`; иначе `bad_bool`. Признак источника, а не подтверждённый отказ |
| `значение_датчика` | текст | Дословно; для прогноза важен текст `Неисправен` у каналов фазы |

Время `1970-01-01 03:00:00` и `…:01` и значения `01.01.1970 03:00:00`/`…:01` — заглушка
устройства: запись сохраняется с пометкой и не переписывается.

#### Журнал: Приложение 1 ТЗ

`format=journal_csv` — тот же, формат определяется по заголовку. Заголовок сравнивается
нестрого, разделитель — запятая или точка с запятой. В Приложении 1 ТЗ типы каналов —
только `2`–`9` и `12`; типов `10` и `11` там нет, и подтверждения технолога по ним нет.

```text
ИД записи журнала;ИД канала данных;ИД типа канала данных;Текущее значение;Дата записи
8100001;demo-700001;12;18,20;29.06.2026 01:15
```

| Столбец | Значение | Правило |
| --- | --- | --- |
| `ИД записи журнала` | может быть пустым, текст | Как `ид_события`; внутри одной минуты задаёт порядок записей |
| `ИД канала данных` | обязательно, текст | Как `ид_канала_данных` |
| `ИД типа канала данных` | может быть пустым, текст | Проверяется по справочнику каналов. Соответствие — предложение команды по названиям типов, технологом заказчика не подтверждено: `9` — `Состояние фазы`, `12` — `Датчик температуры`, `4` — `Датчик дыма`, `6` — `Газовый датчик`, `7` — `Состояние насоса`, `8` — `Состояние вентилятора`, `3` — `Переключатель`, `5` — `Датчик движения`, `2` — контакты (`КД Дверь`, `КД АВ`, `КД Люк`, `9-секционный люк`). Противоречие — `channel_type_conflict`; ID `10`, `11` и другие не проверяются |
| `Текущее значение` | текст | Дословно; `18,20` остаётся текстом |
| `Дата записи` | обязательно | `ДД.ММ.ГГГГ ЧЧ:ММ[:СС]` или `ГГГГ-ММ-ДД ЧЧ:ММ[:СС]`, московское время. Без секунд — допустимо, в отчёте заметка «время с точностью до минуты». Ошибка даты — `bad_date`, времени — `bad_time` |

Признака тревожности в этом формате нет: у записей он «не передан» (`alarm_not_provided`
в отчёте), а не `false`. Если та же запись позже придёт с признаком (выгрузка
организаторов или пачка API), признак дополняется.

### После запуска: поток через API

1. Администратор выдаёт токен (раздел [«Токен»](#токен-интеграции)) и передаёт
   его владельцу системы-источника по защищённому каналу.
2. Система-источник отправляет новые записи пачками. Рекомендуемый ритм — одна пачка
   раз в 5–60 с, до 5 000 записей.
3. Каждая пачка обрабатывается в порядке поступления. Записи сохраняются в базе и
   видны в исходных сообщениях, затем пересчитывается прогноз.
4. **На стенде один поток.** Время данных одно для всех пользователей и идёт только вперёд.
   Запись с датой позже текущих данных сдвигает время прогноза у всех: за сутки без данных
   выдачи будут без карточек. Вернуть время назад можно только восстановлением базы. Для
   проверки подключения отправлять записи внутри периода данных стенда, как пример ниже, а не
   с датой «сегодня».

## Токен интеграции

Токен выдаёт администратор на сервере. Команда печатает его **один раз**. В базе
хранится только SHA-256 токена; восстановить токен нельзя, только выдать новый.

```sh
# На сервере, в каталоге текущего выпуска (deploy/README.md, раздел «Токены интеграции»):
dc exec api python -m infra_pulse_backend.admin --actor <администратор> \
  token create --name scada-ods-1
# token_id: tok-1a2b3c4d5e6f
# name:     scada-ods-1
# token:    ipk_...   <- показывается один раз

dc exec api python -m infra_pulse_backend.admin token list          # без секретов
dc exec api python -m infra_pulse_backend.admin token revoke tok-1a2b3c4d5e6f
dc exec api python -m infra_pulse_backend.admin token revoke --name scada-ods-1
```

`dc` — функция из [deploy/README, раздел 6](../deploy/README.md#6-состояние-и-логи):
`docker compose` с файлами и `.env` стенда. Локально, с корневым `compose.yaml`, из
корня репозитория — тот же CLI в контейнере `api`:

```sh
docker compose exec api python -m infra_pulse_backend.admin --actor <администратор> \
  token create --name scada-ods-1
docker compose exec api python -m infra_pulse_backend.admin token list
```

С `--json` команда печатает JSON с полем `token` — так токен удобно взять в переменную
([пример](#сквозная-проверка-за-5-минут)).

- Имя интеграции — латиница в нижнем регистре, цифры, `.`, `_`, `-`, до 64
  символов. В журнале действий и в `uploaded_by` вызывающий выглядит так:
  `integration:<имя>`.
- Отзыв действует со следующего запроса. `last_used_at` показывает последнее
  использование.
- Замена токена: выдать новый с тем же именем, переключить систему-источник,
  отозвать старый по `token_id`. Пачки обоих токенов одного имени делят
  пространство `batch_id`, поэтому повтор после замены остаётся идемпотентным.
- Выдача, просмотр списка и отзыв записываются в `audit_events`:
  `integration_token.created`, `.listed` и `.revoked`, с автором из `--actor`
  или `cli:<пользователь ОС>`.
- Токен даёт только право `ingest`: отправку пачек и чтение статуса своих пачек.
  Прогнозы, журнал, решения, загрузку CSV и отчёты он не открывает (403).
- Токен передаётся только в заголовке `Authorization`, не в URL. Cookie не нужны,
  поэтому заголовок `X-CSRF-Token` к запросам с токеном не требуется.

## Формат пачки

`Content-Type: application/json` (обязателен), UTF-8. Тело — объект с полями `batch_id` и `records`.
Та же пачка в XML — [ниже](#формат-xml): поля и правила те же, отличается только запись.

```json
{
  "batch_id": "scada-ods-1-20260630T120000-000184",
  "records": [
    {
      "event_id": "9000001",
      "channel_id": "demo-700001",
      "date": "2026-06-30",
      "time": "11:59:58",
      "alarm": false,
      "value": "28"
    },
    {
      "ид_события": "9000002",
      "ид_канала_данных": "demo-700002",
      "дата": "2026-06-30",
      "время": "11:59:59",
      "тревожное": false,
      "значение_датчика": "Неисправен"
    },
    {
      "event_id": "9000003",
      "channel_id": "demo-700003",
      "event_at": "2026-06-30T09:00:00Z",
      "alarm": false,
      "value": "Обрыв; ТО"
    }
  ]
}
```

Время записей примера — 30.06.2026 около 12:00 МСК, внутри периода данных стенда. Каналы
`demo-700001`…`demo-700003` синтетические, в справочнике заказчика их нет. У всех записей
`alarm` = `false`, поэтому пример не добавляет тревожных сообщений в «Сейчас» и на «Схему».
Время записей должно идти по порядку и продолжать поток: запись с датой позже текущих данных
сдвигает время прогноза для всех пользователей стенда ([ниже](#после-запуска-поток-через-api)).

**Формат Приложения 1 ТЗ** (`ИД записи журнала`, `ИД типа канала данных`, `Текущее значение`,
`Дата записи`, без признака тревожности) принимается только файлами CSV или XLSX через раздел
«Загрузка» ([выше](#до-запуска-история-csv-или-xlsx)). В API такая запись — 422: поле `alarm`
обязательно, а поля с другими именами считаются лишними.

| Поле JSON | Колонка CSV | Тип | Правило |
| --- | --- | --- | --- |
| `batch_id` | — | строка 1–128, `[A-Za-z0-9._:-]` | Ключ идемпотентности пачки, уникален в пределах интеграции |
| `event_id` или `ид_события` | `ид_события` | строка 1–64 или целое, обязательно | Хранится как текст; уникальным не считается |
| `channel_id` или `ид_канала_данных` | `ид_канала_данных` | строка 1–64 или целое, обязательно | Канал из справочника; неизвестный канал принимается с неизвестным объектом |
| `date` + `time` или `дата` + `время` | `дата`, `время` | `YYYY-MM-DD` и `HH:MM:SS` | Местное время Москвы, UTC+03:00, как в CSV |
| `event_at` | — | ISO 8601 со смещением | Вместо `date` + `time`; оба варианта сразу — ошибка |
| `alarm` или `тревожное` | `тревожное` | `true` / `false`, обязательно | Тревожный признак источника. Это не подтверждённый отказ; строки `"t"`/`"true"` не принимаются |
| `value` или `значение_датчика` | `значение_датчика` | строка до 1 000 символов, обязательно | Хранится **дословно**; числа тоже строкой: `"28"`, `"0.01"`. `"1,5"` остаётся текстом |

- **Часовой пояс.** `date` и `time` — местное московское время без перехода на летнее
  время, как в выгрузке CSV. `event_at` обязан содержать смещение (`Z`, `+03:00`);
  время без смещения отклоняется.
- Лишние поля в записи или пачке — ошибка 422. Имена полей одной записи задаются
  либо по-английски, либо как в CSV.
- **Ключ совпадения** — канал, момент времени (в UTC), `ид_события` и значение.
  Повторная отправка уже принятой записи, в том числе после CSV и после засева истории
  на стенде, не создаёт дубль и учитывается в `rows_duplicate`. Сверка идёт по самому
  ключу, а не по внутреннему идентификатору строки (с 29.09.2026).
- **`batch_id`.** Пример: `<интеграция>-<время формирования>-<номер>`. Новая пачка —
  новый `batch_id`. Повтор после сетевой ошибки, таймаута, 5xx или 429 — **тот же
  `batch_id` и те же байты**. После статуса `failed` — новый `batch_id`: повтор с прежним
  вернёт прежний отчёт ([статус пачки](#статус-пачки)).

## Формат XML

`Content-Type: application/xml` или `text/xml`. Пачка та же, что в JSON: после разбора XML
она проверяется той же схемой (`ObservationBatch`), с теми же лимитами, ключом совпадения,
идемпотентностью, журналом действий и тем же worker.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<batch batch_id="scada-ods-1-20260630T120000-000184">
  <record>
    <event_id>9000001</event_id>
    <channel_id>demo-700001</channel_id>
    <date>2026-06-30</date>
    <time>11:59:58</time>
    <alarm>false</alarm>
    <value>28</value>
  </record>
  <record>
    <ид_события>9000002</ид_события>
    <ид_канала_данных>demo-700002</ид_канала_данных>
    <дата>2026-06-30</дата>
    <время>11:59:59</время>
    <тревожное>false</тревожное>
    <значение_датчика>Неисправен</значение_датчика>
  </record>
  <record>
    <event_id>9000003</event_id>
    <channel_id>demo-700003</channel_id>
    <event_at>2026-06-30T09:00:00Z</event_at>
    <alarm>false</alarm>
    <value>Обрыв; ТО</value>
  </record>
</batch>
```

| Элемент | Правило |
| --- | --- |
| `<batch>` | Корень, без пространства имён. `batch_id` — атрибут `<batch batch_id="…">` или дочерний элемент `<batch_id>…</batch_id>`, не оба сразу. Другие атрибуты и элементы — лишние поля (422) |
| `<record>` | Одна запись журнала; все `<record>` — прямо внутри `<batch>`, без обёртки `<records>`. Атрибутов нет |
| Поля записи | Дочерние элементы `<record>` с именами полей JSON, по-английски или как в CSV (`<ид_события>`, `<значение_датчика>` …). Порядок любой, каждое поле не больше одного раза. Внутри поля — только текст: без атрибутов и вложенных элементов |
| Текст поля | Берётся дословно, вместе с пробелами: `<value> 28 </value>` — это `" 28 "`. Пустой элемент `<value/>` — пустая строка. Спецсимволы — `&amp;`, `&lt;`, `&gt;` или `<![CDATA[…]]>` |
| `alarm` / `тревожное` | Ровно `true` или `false`. Другие значения (`t`, `1`, `TRUE`) — 422, как `"t"` в JSON |
| Время | `date` + `time` (МСК) или `event_at` со смещением — как в JSON |
| Кодировка | UTF-8. Другая кодировка допустима, только если указана в XML-объявлении (`<?xml … encoding="windows-1251"?>`); `charset` в `Content-Type` не учитывается |

**Отличия от JSON.**

- В XML всё — текст: идентификаторы и значения передаются как в CSV, число и строка не
  различаются. `alarm` переводится в логическое значение только из `true` и `false`.
- `<!DOCTYPE>` запрещён целиком: DTD, объявления сущностей (внутренние и внешние),
  внешние ссылки. Такая пачка отклоняется до разбора содержимого — 422 `xml_forbidden`.
  Сервис не загружает внешние ресурсы. Комментарии и инструкции обработки игнорируются.
- Тело хранится как есть, в файле `.xml`; в статусе пачки `file_name` —
  `observations-<batch_id>.xml`, `source_container` — `xml`.
- **Повтор.** Идемпотентность сравнивает байты тела. XML и JSON одной и той же пачки — разные
  тела: повтор с тем же `batch_id` в другом формате или переформатированный XML получит 409
  `batch_id_conflict`. Повторять нужно в том же формате, тем же файлом. Совпадающие записи из
  разных пачек (в том числе JSON и XML) сохраняются один раз по ключу совпадения.
- Ответы (202, 200, ошибки, статус пачки) — JSON, заголовок `Accept` не учитывается.

**Ошибки XML** — 422, в том же формате, что ошибки схемы (`detail` — список, у ошибок в
записи есть `record` — номер `<record>` с 1). Ошибок структуры XML в ответе не больше 100:
на сотой разбор останавливается. Больше 5 000 `<record>` — 413 `too_many_records` до разбора
записей.

| `type` | Причина |
| --- | --- |
| `xml_forbidden` | Есть `<!DOCTYPE>`, объявление сущности или внешняя ссылка |
| `xml_invalid` | XML построен неверно (незакрытый тег, неизвестная сущность `&x;`, неверная кодировка); `input` — строка и столбец |
| `xml_structure` | Корень не `<batch>`, пространство имён, текст вне полей, атрибуты у `<record>` или поля, вложенные элементы в поле, обёртка `<records>` |
| `xml_duplicate_field` | Поле записи или `batch_id` указано дважды |
| `extra_forbidden`, `missing`, `bool_type`, … | Обычные ошибки схемы: лишнее или отсутствующее поле, неверное значение — как в JSON |

```json
{"detail": [{"type": "xml_forbidden", "loc": ["body"],
  "msg": "DTD, entity declarations and external references are not allowed",
  "input": "DTDForbidden"}]}
```

## Отправка

```sh
curl -sS -X POST https://<стенд>/api/v1/observations \
  -H "Authorization: Bearer $INFRA_PULSE_TOKEN" \
  -H "Content-Type: application/json" \
  --data-binary @batch.json
```

Пачка XML — тем же запросом с другим заголовком:

```sh
curl -sS -X POST https://<стенд>/api/v1/observations \
  -H "Authorization: Bearer $INFRA_PULSE_TOKEN" \
  -H "Content-Type: application/xml" \
  --data-binary @batch.xml
```

На туннельном стенде адрес — `http://127.0.0.1:8000/api/v1/observations`
(SSH-туннель, [deploy/README](../deploy/README.md#4-доступ-через-ssh-туннель)); в локальном
Compose — тот же адрес с портом `API_PORT`.
`--data-binary` отправляет файл без изменений. При повторе байты должны совпасть,
иначе ответ будет 409. Без `-H "Content-Type: …"` curl ставит
`application/x-www-form-urlencoded`, и ответ будет 415.

Пример XML проверен 28.09 в прежней версии (другие каналы, одна запись с `alarm` = `true`)
на локальном API в режиме `received` (uvicorn, worker, одноразовый PostgreSQL 14, токен из
CLI): 202 `queued`, повтор тех же байтов — 200, тот же `batch_id` в JSON — 409, после
worker — `published`, 3 записи, `source_container: xml`, файл в `uploads` совпал с
отправленным байт в байт; «billion laughs» и внешняя сущность — 422 `xml_forbidden`;
`text/plain` и запрос без `Content-Type` — 415. Текущий пример (каналы `demo-…`,
`alarm` = `false`) проверен 29.09 автотестами и в локальном Compose: JSON и XML →
`published` ([сквозная проверка](#сквозная-проверка-за-5-минут)). На стенде не проверялось.

Ответ 202 — пачка сохранена и поставлена в очередь:

```json
{
  "id": "imp-20260927T123001-3f2a9c1b7d4e",
  "format": "journal_json",
  "file_name": "observations-scada-ods-1-20260630T120000-000184.json",
  "sha256": "…",
  "uploaded_by": "integration:scada-ods-1",
  "status": "queued",
  "timings": [{"stage": "store", "seconds": 0.002}]
}
```

## Сквозная проверка за 5 минут

Путь «пустой стек → справочники → журнал → токен → пачки JSON и XML → `published` →
экраны» на своём компьютере, без данных заказчика: файлы — [синтетические примеры](#синтетические-примеры).
Нужны Docker с Compose, `curl` и `python3`; команды — из корня репозитория, в одном
терминале. Пять минут — без сборки образов: первая сборка занимает от 4 до 16 минут в
зависимости от скорости загрузки пакетов.

**1. Стек в режиме `received`.** В быстром старте README режим `fixture`: там загрузки и
пачки только имитируются (202 с `simulated: true`, статус пачки — 404). Локально вход
выключен (`dev_stub`): запросы без сессии идут от `local-operator` со всеми ролями.

```sh
export WEB_PORT=8080 API_PORT=8000 DB_PORT=5432   # если порт занят: 18080 18000 15432
INFRA_MODE=received docker compose up --build -d --wait
export API=http://127.0.0.1:$API_PORT
curl -sS $API/health/ready; echo    # "status":"ready","stage":"observations_only"
```

Если сборка прервалась на загрузке пакета (`Failed to download … network timeout`) —
повторить ту же команду: готовые слои берутся из кэша.

**2. Справочники и журнал.** Worker обрабатывает загрузки по одной в порядке поступления,
поэтому справочник каналов идёт первым. Каждая команда отвечает 202.

```sh
for kind in channels objects states; do
  curl -sS -o /dev/null -w '%{http_code}\n' -F format=reference_${kind}_csv \
    -F file=@docs/examples/reference-$kind.csv $API/api/v1/imports
done
for name in journal-2026-06-29 journal-appendix1-2026-06-29; do
  curl -sS -o /dev/null -w '%{http_code}\n' -F format=journal_csv \
    -F file=@docs/examples/$name.csv $API/api/v1/imports
done
sleep 3
curl -sS "$API/api/v1/imports?limit=20" | python3 -c 'import json,sys
for i in json.load(sys.stdin)["items"]: print(i["status"], i.get("error_code") or "-", i["rows_accepted"], i["file_name"])'
```

Все пять — `published`: 24 записи Приложения 1 ТЗ, 134 записи журнала, 11 состояний,
3 объекта, 16 каналов (список — от новых к старым). Если какая-то загрузка ещё `queued` или
`recomputing`, повторить последнюю команду.

**3. Токен интеграции** — CLI в контейнере `api`; токен печатается один раз, здесь сразу
попадает в переменную.

```sh
export INFRA_PULSE_TOKEN=$(docker compose exec -T api python -m infra_pulse_backend.admin \
  --actor demo-admin token create --name demo --json \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["token"])')
```

**4. Пачки JSON и XML.** Ответ 202 с `id` пачки и `"uploaded_by": "integration:demo"`.

```sh
curl -sS -X POST $API/api/v1/observations -H "Authorization: Bearer $INFRA_PULSE_TOKEN" \
  -H "Content-Type: application/json" --data-binary @docs/examples/batch-000184.json; echo
curl -sS -X POST $API/api/v1/observations -H "Authorization: Bearer $INFRA_PULSE_TOKEN" \
  -H "Content-Type: application/xml" --data-binary @docs/examples/batch-000185.xml; echo
curl -sS -H "Authorization: Bearer $INFRA_PULSE_TOKEN" $API/api/v1/observations/<id из ответа>
```

Обе пачки — `published`: JSON — 3 записи, `forecast_generation` 3; XML — 2 записи,
`source_container: xml`. Повтор первой команды — 200 и тот же отчёт.

**5. Где смотреть результат.**

- `http://127.0.0.1:$WEB_PORT/upload` — «Загрузка»: история из 7 загрузок, у каждой отчёт
  (этапы, строки, период событий, версия справочника). У пачки JSON — «новых 3».
- `/journal` — «Журнал»: карточек нет, под таблицей «Прогноз не выдан … Синт. объект 1–3,
  30.06, 00:00 — недостаточно истории». Первая пачка перевела время данных через срез
  30.06.2026 00:00, но у объектов история один день, а списку нужны 365 суток.
- `/forecast` — «Прогноз»: «0 из 10 карточек» и блок «Сейчас» — тревожные сообщения СМВУ
  за сутки до 30.06 12:04: «Синт. объект 2», «Неисправен» и «Обесточен» 29.06 19:40–19:41.
- `/scheme` — «Схема объектов»: 3 объекта, линии по пикетам из названий каналов.
- `curl -sS $API/api/v1/forecast-state` — `data_as_of` 30.06.2026 12:04:58 МСК (09:04:58Z).

**6. Отказ по заголовку** (необязательно). Журнал, объявленный справочником каналов, —
`failed`, `bad_header`; какие столбцы ожидались, отчёт не называет — они в
[форматах файлов](#форматы-файлов).

```sh
curl -sS -F format=reference_channels_csv -F file=@docs/examples/journal-2026-06-29.csv \
  $API/api/v1/imports
```

**7. Карточки с оценкой** (необязательно, последним шагом): нужна история объектов не меньше
365 суток. Скрипт нагрузочного теста загружает синтетический справочник 76 каналов на
19 объектах и журнал за 400 суток, заканчивающийся сегодня (около 20 с, нужен
`uv sync --locked`):

```sh
uv run --locked python backend/scripts/load_test.py --base-url $API --dev --seed-synthetic \
  --users 1 --duration 5
```

После него «Прогноз» показывает карточки с оценкой. Его справочник каналов становится
действующим вместо справочника примеров, время данных уходит на сегодня — на своём стенде
это допустимо, на общем нет.

**8. Уборка** — контейнеры, тома с данными и собранные образы:

```sh
docker compose down -v
docker image rm infra-pulse-msk-api infra-pulse-msk-worker infra-pulse-msk-migrate infra-pulse-msk-web
```

**Проверено 29.09.2026** на macOS arm64, Docker Desktop 28.3.2, Compose 2.38.2, в
отдельном Compose-проекте (`COMPOSE_PROJECT_NAME`, порты 28180/28100/25532 — 5432 на машине
занят). Первая сборка — 16 мин (медленная загрузка пакетов); повторная сборка после правки
README прервалась на таймауте загрузки. Затем блоки команд этого раздела выполнены
скриптом подряд на уже собранных образах, с уборкой шага 8: подъём стека — 18 с, шаги

## Документация API (Swagger UI)

Адрес — https://infra-pulse.ru/api/docs (на своём стенде — `https://<стенд>/api/docs`),
схема OpenAPI — `/api/openapi.json`. Страница открыта без входа и только описывает API:
запросы из неё («Try it out») проверяются так же, как запросы любой программы. На стенде
документацию включает `INFRA_PUBLIC_DOCS=true` ([deploy/README](../deploy/README.md#11-публичный-доступ)).

**Пачка с токеном интеграции.**

1. Нажать «Authorize» вверху страницы. В блоке `integrationToken (http, Bearer)` вставить
   токен `ipk_...` без слова `Bearer`, нажать «Authorize», затем «Close».
2. Открыть `POST /api/v1/observations` → «Try it out». В списке типа тела выбрать
   `application/json` или `application/xml`: в поле уже стоит синтетический пример
   ([JSON](#формат-пачки) или [XML](#формат-xml)).
3. «Execute». Swagger отправит `Authorization: Bearer ipk_...`; ответ 202, повтор того же
   тела — 200 ([ответы](#ответы)). Примеры JSON и XML — одна пачка с одним `batch_id`,
   поэтому второй формат после первого вернёт 409 `batch_id_conflict`. Статус —
   `GET /api/v1/observations/{import_id}` с тем же токеном.

Пачка из примера на рабочем стенде сохраняется как настоящая и попадает в его журнал;
для проверки без записи достаточно чтения схемы и примеров. Токен хранится только в памяти
вкладки: он пропадает при закрытии или обновлении страницы и по «Logout» в «Authorize».

**Чтение под сессией.** GET-маршруты (прогноз, журнал, отчёты — в пределах роли) работают
по cookie сессии: войти в веб-интерфейс того же сайта в этом браузере, затем «Try it out» →
«Execute».
Поле `sessionCookie` в «Authorize» заполнять не нужно: страница не может поставить cookie,
браузер отправляет её сам. Запись под сессией дополнительно требует `csrfToken` — значение
cookie `__Host-infrapulse-csrf`. Токен интеграции на остальных маршрутах даёт 403
`forbidden_role`, без сессии и токена ответ — 401.

## Лимиты

| Лимит | Значение | Ответ при превышении |
| --- | --- | --- |
| Размер тела | 5 MiB | 413 `batch_too_large`; тело дочитывается не до конца |
| Записей в пачке | 1–5 000 | 413 `too_many_records`; пустая пачка — 422 |
| Длина `value` | 1 000 символов | 422 |
| Частота | 60 пачек в минуту на токен (`INFRA_INTEGRATION_REQUESTS_PER_MINUTE`) | 429 `rate_limited` с `Retry-After` |

Счётчик частоты хранится в памяти процесса API и сбрасывается при его перезапуске.
Лимит проверяется до разбора тела, поэтому в него входит каждый `POST`, в том числе
повтор с тем же `batch_id` (ответ 200 или 409) и пачка с ошибкой 422.
Опрос статуса в лимит не входит.

## Ответы

| Код | `detail` | Значение | Что делать |
| --- | --- | --- | --- |
| 202 | — | Пачка принята и поставлена в очередь | Сохранить `id`, при необходимости проверить статус |
| 200 | — | Повтор уже принятой пачки: тот же `batch_id` и те же байты. Возвращается сохранённый отчёт, в том числе `failed`; пачка заново не обрабатывается | Ничего; повтор безопасен. Если в отчёте `failed` — исправить причину и отправить записи новой пачкой с новым `batch_id` |
| 401 | `invalid_token` | Токена нет, он неизвестен или отозван | Проверить токен, обратиться к администратору |
| 401 | `not_authenticated` | Запрос без токена на публичном стенде | Добавить `Authorization: Bearer …` |
| 403 | `forbidden_role` | У вызывающего нет права `ingest`: вход диспетчера или аналитика | Использовать токен интеграции |
| 409 | `batch_id_conflict` | `batch_id` уже занят пачкой с другими байтами | Не повторять; сформировать новый `batch_id` |
| 413 | `batch_too_large` / `too_many_records` | Больше 5 MiB или 5 000 записей | Разбить пачку |
| 415 | `unsupported_media_type` | `Content-Type` не JSON (`application/json`) и не XML (`application/xml`, `text/xml`) или его нет. Проверяется до токена, как размер | Указать заголовок формата тела |
| 422 | список ошибок | Тело не соответствует схеме, не JSON / не XML по заголовку, в XML есть DTD или сущности ([ошибки XML](#формат-xml)). У ошибок в записях есть `record` — номер записи с 1, и `loc` | Исправить записи; пачка целиком не принята |
| 429 | `rate_limited` | Превышен лимит частоты | Повторить после `Retry-After` с тем же `batch_id` |
| 503 | `imports_storage_unavailable`, `upload_storage_unavailable`, `auth_storage_unavailable`, `imports_not_configured` | БД или хранилище недоступны либо не настроены | Повторить позже с тем же `batch_id` |

Пример 422:

```json
{"detail": [{"type": "bool_type", "loc": ["body", "records", 1, "alarm"],
  "msg": "Input should be a valid boolean", "input": "t", "record": 2}]}
```

**Повтор.** Сеть, таймаут, 5xx и 429 — повторять с **тем же `batch_id` и теми же
байтами** (в том же формате, JSON или XML). Интервалы — с экспоненциальной паузой 1, 2, 4 … до 60 с; при 429
использовать `Retry-After`. Если первая попытка всё же дошла, повтор вернёт 200 с
тем же отчётом. На 4xx, кроме 429, повторять не нужно: без исправления ответ не
изменится.

## Статус пачки

```sh
curl -sS -H "Authorization: Bearer $INFRA_PULSE_TOKEN" \
  https://<стенд>/api/v1/observations/imp-20260927T123001-3f2a9c1b7d4e
```

Токен видит только свои пачки; чужой или неизвестный `id` — 404 `batch_not_found`.
Администратор видит все пачки и в разделе «Загрузка».

| Статус | Значение |
| --- | --- |
| `queued` | Сохранена, ждёт worker |
| `parsing` | Разбор и запись |
| `imported` | Записи в базе и видны диспетчеру; прогноз ещё не пересчитан. Итоговым статус остаётся, только если в рабочем scope ещё нет ни одной принятой записи журнала |
| `recomputing` | Пересчёт прогноза |
| `published` | Прогноз пересчитан: `forecast_generation`, новые и снятые карточки. Если все записи пачки уже были в базе, пересчёта нет: текущий `forecast_generation` и заметка «Новых записей нет: прогноз не пересчитывался» (с 29.09.2026) |
| `duplicate` | Те же байты уже приняты в другой загрузке; новых записей нет |
| `failed` | `error_code`: `reference_missing` (нет справочника каналов), `no_valid_rows`, `recompute_failed` (записи сохранены, пересчёт не удался), `internal_error`. Повтор с тем же `batch_id` вернёт 200 и этот же отчёт: пачка заново не обрабатывается. После исправления причины (например, загрузки справочника) отправить записи новой пачкой с новым `batch_id` |

Счётчики: `rows_total = rows_accepted + rows_duplicate + rows_quarantined`;
`unknown_channels` — каналы вне справочника. Их записи сохранены с неизвестным
объектом. `quarantine_sample` — до 20 отклонённых записей: `line_no` — номер
записи в `records` с 1, и причина. Причины: `bad_date` (нет такой даты),
`bad_time`, `bad_bool`, `empty_channel`, `bad_encoding` (символ NUL или
некорректный Unicode), `value_too_long`. Остальные записи пачки приняты.

## Задержка и пропускная способность

Требование OPS-01 — не более 300 с от поступления данных до результата. Замер от
27.09.2026 выполнен на локальной машине, не на стенде, с пересчётом прогноза на scope с
годом истории 1 000 каналов (на стенде путь «пачка → `published`» не замерялся):
- пачка из 1 000 записей доходит до `published` за 0,19 с (p50) и 0,22 с (p95);
- пачка из 5 000 записей — за 0,3–0,4 с;
- 10 пачек по 5 000, отправленные подряд, опубликованы все за 2,8 с.

Подробности — в [OPERATIONS](OPERATIONS.md#замер-задержки-api-ингеста-27092026).
Пачки обрабатываются по одной в порядке поступления. Поэтому рекомендуемый ритм — одна
пачка раз в 5–60 с. Слишком частые мелкие пачки только удлиняют очередь.

Записи одного канала лучше отправлять в порядке времени. Запись старше последней
принятой записи этого канала принимается, но пересчёт тогда перестраивает историю
канала; в замере это увеличивало время пачки до нескольких секунд.

## Очередь сообщений и XML

- **Приём — REST.** ТЗ допускает «API или очередь сообщений»; внешний брокер (Kafka,
  RabbitMQ) не используется. Внутри сервиса файлы и пачки проходят надёжную очередь заданий
  в PostgreSQL: захват `FOR UPDATE SKIP LOCKED`, lease с перехватом задания после сбоя
  процесса, пробуждение worker по `LISTEN/NOTIFY`, строгий порядок поступления.
  Подключение брокера — planned: адаптер читает сообщения и отправляет их в этот же приём
  с тем же `batch_id`, поэтому идемпотентность и дедупликация сохраняются.
- **Формат — JSON или XML** ([формат XML](#формат-xml)): обе записи пачки проверяются одной
  схемой `ObservationBatch`, второго контракта нет. Ответы — JSON; ответы в XML по `Accept` —
  planned.
- **Справочники** загружает администратор файлами; автоматической синхронизации реестров нет.

## Безопасность и границы

- Публичный стенд принимает запросы только по HTTPS (Caddy, TLS 1.2+).
- XML разбирается `defusedxml` с запретом `<!DOCTYPE>`: сущности («billion laughs»), внешние
  DTD и сущности (XXE) отклоняются до разбора содержимого, внешние ресурсы не загружаются.
- Токен даёт только право `ingest`. Вход через каталог LDAP это право не даёт, кроме
  роли `admin`: администратор может отправить пачку из своей сессии, с `X-CSRF-Token`.
- Каждая принятая пачка записывается в `audit_events`: `observations.received`, автор
  `integration:<имя>`, роль, `batch_id`, число записей, SHA-256, размер, `token_id`,
  request id. Эта запись фиксируется в одной транзакции с загрузкой. Повтор с тем же
  `batch_id` новую запись не создаёт.
- Сервис не обращается к системам заказчика и не отправляет им заявки.
