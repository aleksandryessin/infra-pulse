готовые `.json` файлы. Этот режим не измеряет задержку в канале заказчика и не
включает внешний коннектор; D07 и OPS-01 ещё открыты.
Не считать содержимое research artifacts автоматически одобренной моделью.
При реализации VPS loader задайте явный read-only mount, например
`INFRA_ARTIFACT_ROOT=/models`, и проверяйте manifest конкретной принятой версии.
Compose сейчас не реализует этот model mount; он входит в этап worker/release.

## Локальный пробный замер received-path, 25.09.2026

`backend/scripts/probe_received_path.py` запускается только против
одноразовой PostgreSQL на loopback и уникального stream с префиксом
`synthetic-probe-`. Сначала запустите API в `received` с тем же stream и
namespace в отдельном терминале:

```sh
INFRA_MODE=received INFRA_DB_DSN='postgresql://127.0.0.1:55432/postgres' \
  INFRA_RECEIVED_NAMESPACE=synthetic-probe \
  INFRA_RECEIVED_STREAM_ID=synthetic-probe-local-1 UV_OFFLINE=1 \
  uv run --locked uvicorn infra_pulse_backend.api.app:app \
  --host 127.0.0.1 --port 8001
```

Затем из корня репозитория:

```sh
INFRA_RECEIVED_DSN='postgresql://127.0.0.1:55432/postgres' UV_OFFLINE=1 \
  uv run --locked --group research python backend/scripts/probe_received_path.py \
  --stream synthetic-probe-local-1 --users 20 --duration 10 \
  --api-pid "$INFRA_API_PID" --db-pid "$INFRA_DB_PID"
```

Значения DSN, stream и API port следует заменить для своей временной БД;
`INFRA_API_PID` задаётся из лога uvicorn, `INFRA_DB_PID` — из `pg_ctl status`.
Оба PID должны быть экспортированы перед командой.
`--base-url` меняет адрес API. `--group research` даёт диагностическому скрипту
`psutil`, не добавляя его в HTTP runtime. Скрипт сначала требует пустой
синтетический stream, затем импортирует одну baseline-запись и партию из
40 обычных записей по умолчанию и одной исходной `alarm=true`.
`--normal-rows` задаёт 25–4999 обычных записей; 4999 достигает лимита импортера
в 5000 записей на партию. ID тревоги подбирается так, чтобы она была за первой
страницей полного списка из 25 записей. Пока 20 клиентов
циклически читают очередь, список новых исходных тревог, объекты и каналы,
скрипт сверяет счётчик новых записей/тревог с импортом, отсутствие тревоги на
первой полной странице и точный `row_uid` в фильтрованном списке. Пауза между
циклами по умолчанию 0.5 с. Скрипт измеряет видимость новой записи в API,
клиентские p50/p95/max и сэмплирует API/DB process tree каждые 0.25 с.
Вывод содержит только агрегаты. `import_to_api_ms` сравнивает часы БД и клиента
на одной машине; `peak_sum_rss_mb` суммирует RSS процессов, включая общие
страницы. Недоступный счётчик IO выводится как `null`, а не как ноль.

## Замер задержки API-ингеста, 27.09.2026

**Что измерено.** Время от начала `POST /api/v1/observations` до статуса пачки.
Путь пакета B1x: пачка → файл в `uploads` → `import_files` (`journal_json`) →
`NOTIFY` → worker. Два прогона:
- в ветке B1x, до слияния B2 — до `imported`: записи в `dispatch_observations` и видны
  в очереди, пересчёт — заглушка;
- после слияния B2 — до `published`: пересчёт и публикация прогноза
  ([ниже](#после-слияния-b2-post--published)).

**Что не измерено.** Путь через Caddy/TLS и сервер.

Требование OPS-01 (ТЗ §9) — не более 300 с. Это локальный пробный замер, а не профиль
нагрузки D08: OPS-01 остаётся planned.

**Среда:**
- macOS, Apple M4 Max (14 ядер, 36 GiB);
- одноразовый PostgreSQL 14.20 из Homebrew с настройками по умолчанию, loopback;
- один процесс uvicorn: `INFRA_MODE=received`, `dev_stub`, запросы с токеном
  интеграции, лимит поднят до 120 пачек в минуту;
- один `python -m infra_pulse_backend.worker` (LISTEN/NOTIFY);
- синтетический справочник из 1 000 каналов;
- записи датированы несколькими секундами раньше текущего времени. Половина
  записей — `date` + `time`, половина — `event_at`, каждая 97-я — `alarm=true`.

Сценарии замера:
- *sequential* — следующая пачка отправляется после завершения предыдущей;
- *burst* — все пачки отправляются подряд, затем опрашиваются каждые 20 мс.

```sh
uv run --locked python backend/scripts/probe_observation_api.py \
  --base-url http://127.0.0.1:8471 --token-file <файл вне репозитория> \
  --batches 20 --records 1000 --mode sequential
```

Скрипт датирует пачки от текущего времени, поэтому запускается только на локальной или
пустой копии. На стенде с историей первая же пачка сдвигает время прогноза у всех
пользователей; SSH-туннель к стенду тоже loopback-адрес, и проверка адреса от этого не защищает.

| Сценарий | POST, p50 / max, с | POST → `imported`, p50 / p95 / max, с | load, p50, с |
| --- | --- | --- | --- |
| 20 × 1 000 записей, sequential | 0,020 / 0,046 | 0,067 / 0,104 / 0,118 | 0,029 |
| 20 × 1 000, burst | 0,016 / 0,037 | 0,440 / 0,823 / 0,883 | 0,045 |
| 5 × 5 000 (0,65 MB), sequential | 0,021 / 0,027 | 0,200 / 0,284 / 0,284 | 0,150 |
| 10 × 5 000, burst (50 000 записей) | 0,028 / 0,058 | 0,854 / 1,768 / 1,768 | 0,159 |

Все 55 пачек дошли до `imported`: 115 000 записей, 0 quarantine, 0 дублей. Тест
`test_5000_record_batch_is_imported_within_seconds` на пустой схеме: пачка 5 000
записей — 0,19 с от POST до `imported`.

Предыдущий прогон на накопленной БД дал более медленные числа. Повтор 20 × 1 000:
p95 0,28 с. Burst 10 × 5 000: max 9,3 с; load двух пачек занял 2,6 и 3,5 с. В новом
прогоне этого не было. Причина не установлена; вероятно, checkpoint при
`max_wal_size` по умолчанию, как в [замере B1](../deploy/README.md#ingestion-worker-и-загрузка-csv).

**Вывод.** До появления B2 задержка приёма — доли секунды на пачку. Воркер один и
обрабатывает загрузки строго по порядку, поэтому очередь из N пачек добавляет примерно
N × (load + пересчёт). Поэтому рекомендуемый ритм для заказчика — одна пачка раз в
5–60 с, до 5 000 записей ([INTEGRATION_API](INTEGRATION_API.md)). Замер на стенде не
выполнялся.

## Локальный старт

```sh
uv sync --locked
uv run --locked pytest
uv run --locked uvicorn infra_pulse_backend.api.app:app --reload --host 127.0.0.1 --port 8000
```

API: `http://127.0.0.1:8000/api/docs`. `GET /health/live` возвращает 200.
`GET /health/ready` возвращает 503 в scaffold. В локальном replay/received с загруженным
snapshot он возвращает 200 и фактический `stage`: `inference_ready` равно true, когда прогноз
опубликован (`stage=forecast_published`), до первой публикации — false (`observations_only`).
`GET /api/v1/risks` — прежний стартовый contract: вне fixture отвечает 410
`risks_replaced_by_forecasts` (прогноз — `/api/v1/forecasts`) и скрыт из схемы API. Для фикстуры:

```sh
INFRA_MODE=fixture uv run --locked uvicorn infra_pulse_backend.api.app:app --host 127.0.0.1 --port 8000
```

Во втором терминале по очереди: `cd frontend`, `npm ci`, `npm run dev`.
Стартовый экран на 5173. Synthetic fixture не содержит вероятности и помечена
`source=synthetic_fixture`. Для replay см. [backend](../backend/README.md) и
[frontend](../frontend/README.md): он работает на bounded PostgreSQL срезе,
а не на live данных. Local reviews выключены по умолчанию; при включении без
аутентификации доступны только для локального теста.

## Docker Compose

```sh
docker compose config --quiet
docker compose up --build
```

Web 8080, API 8000, пустая PostgreSQL 5432. Порты привязаны к localhost. Перед api и
worker разовый сервис `migrate` применяет миграции владельцем и включает рантайм-роль
`infra_pulse_app`; api и worker подключаются ею (пароль — `INFRA_DB_APP_PASSWORD`, по
умолчанию локальный из `compose.yaml`).
Если порты заняты, задайте `WEB_PORT`, `API_PORT`, `DB_PORT` в окружении Compose.
При нативном запуске API порт задаёт `uvicorn --port`, а Vite proxy можно настроить
через `API_PROXY_TARGET=http://127.0.0.1:18000 npm run dev` в frontend.
Для fixture: `INFRA_MODE=fixture docker compose up --build`. В `fixture` загрузки и пачки
не сохраняются (ответ `simulated: true`). Сквозной путь «справочник → журнал → токен →
пачка → `published`» — `INFRA_MODE=received docker compose up --build` и синтетические
файлы `docs/examples/`: [сквозная проверка](INTEGRATION_API.md#сквозная-проверка-за-5-минут).
Текущий Compose не загружает replay snapshot и не включает его настройки.
Поэтому один запуск БД не превращает readiness в 200. Compose healthcheck
проверяет только liveness. Остановка без удаления данных: `docker compose down`.

Пароли в Compose — только локальный development. Общий сервер требует `.env`
с отдельным паролем, закрытую БД, TLS и auth до публикации URL.
Нельзя применять этот Compose как production-конфигурацию без P-05.
Корневой Compose по-прежнему не загружает replay snapshot; для сервера это делает
отдельный override, описанный ниже.

## Подготовка release evidence (P-05, planned)

Критерии и обязательные пределы заданы в SPEC; здесь порядок проведения проверок.
Worker, production migrations и release tooling ещё не реализованы, поэтому команды этих
проверок добавляются вместе с соответствующей реализацией.

1. По ML-06/DELIV-01 выбрать bundle и image, сверить manifest и научный допуск model card.
2. По OPS-03 проверить миграции и готовность данных; выполнить smoke batch на ограниченном периоде.
3. По ML-06 сравнить loaded prediction с offline результатом на одних features.
4. По API-07 проверить writer/scheduler, retries и failed run audit.
5. Измерить полный receive+queue+ingestion+feature+inference+DB+UI lag
   и время прогноза по объекту на профиле D08; собрать timings/error/resource logs,
   сверить их с OPS-01 и UI-03. Virtual replay time записывать отдельно от wall clock.
6. По SEC-01–SEC-04 проверить TLS, scope матрицу, audit и LDAP adapter на тестовом каталоге.
7. По OPS-02/D09 восстановить PostgreSQL, bundle и необходимые manifests из внешней
   копии на чистый экземпляр. Записать время и сверить целостность прогнозов/решений/audit.
8. По OPS-03 выполнить rollback совместимых image/bundle/policy; при несовместимой
   миграции подготовить и проверить отдельный путь восстановления.
9. Проверить свободный диск с учётом raw/parquet/spill/backup и временных файлов;
   собрать evidence этих шагов в manifest DELIV-01.

Кандидат механизма scheduler — systemd timer, bounded batch и lock. Период пробуждения
выбирается по D07/D08; cadence прогнозных точек фиксируется отдельно по D05.
Проверка новых входов, пересчёт прогноза и обновление UI — разные интервалы.
До выбора протокола минутный запуск worker не считается принятой частотой scoring.
Метрики: source lag, scoring duration, channels scored/abstained, failures, model
version. «Нет новых событий» не считать outage без agreed heartbeat.

Для начального стенда планируется один worker с bounded RAM, immutable partitions
и checkpoint. Полный backfill запускается отдельной операцией с ресурсным окном,
чтобы не конкурировать с демонстрацией. Параметры VPS — D12; резервная копия хранится
вне него по OPS-02. Один сервер не обеспечивает HA.

## GitHub Actions: что проверяется

Workflow [Checks](../.github/workflows/ci.yml) запускается при push и pull request.
Выполняются три job на Ubuntu:

| Job | Назначение |
| --- | --- |
| Backend | Установка полного Python-окружения, imports, конфигурация MLflow, Ruff/format, все pytest с тестовой PostgreSQL 17 для received/replay интеграций, совпадение generated contracts |
| API without research | Минимальная установка, отсутствие research/ML-пакетов, API и проверки границ компонентов; тесты HTTP parity helpers не требуют DuckDB |
| Frontend | npm ci, генерация TS из OpenAPI, TypeScript/Vite build, тест обработчика обновления и проверка отсутствия расхождения TS-схемы |

Это CI, без deployment на VPS и без обучения на реальных данных. Развёртывание —
отдельный ручной workflow `Deploy stand` ([runbook](../deploy/README.md)); он не
запускается при push. Тесты используют
синтетические fixtures и одноразовую PostgreSQL; фактический результат нового
backend job нужно проверить после push. Один failed job делает весь run красным;
warnings следует читать отдельно от упавшего шага. Эти jobs не заменяют
браузерную приёмку UI, Docker smoke, клиентский сквозной сценарий или проверку
качества модели.

Для диагностики открыть failed job и первый упавший step. Исправление проверяется
на новом commit/push; кнопка Re-run повторяет прежнюю версию. UTF-8 JSON/notebooks
читаются с явным `encoding="utf-8"`, независимо от системной локали.
