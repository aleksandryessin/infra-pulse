Состояние на 29.09.2026: исследовательский код для GRU, LSTM, TCN и Transformer
Encoder; обучение на реальных данных проведено 28.09 — 32 оценки (30 моделей и два
baseline), прирост над статичным списком не подтверждён
([итог](#итог-на-реальных-данных--28092026),
[отчёт](../../reports/phase-sequence-2026-09-28.md)). Это диагностика на уже
просмотренной истории, а не новая проверка. Продукт продолжает использовать
[статичный список v9](../sensor-failure/FINAL_V9.md).

## Запуск из корня репозитория

Установка требует интернета один раз; последующие команды работают локально.
PyTorch находится в отдельной группе `sequence`, API и worker её не используют.
На Linux обычный wheel PyTorch может дополнительно загрузить CUDA-библиотеки.

```sh
uv sync --locked --group train --group research --group sequence
make check-sequence
make sequence-smoke
```

`sequence-smoke` обучает все четыре сети и компактный CatBoost на полностью
синтетических данных: один fold, один seed, две эпохи, CPU. Результат —
`data-science/artifacts/sequence-v1/smoke/run.json`. Повтор требует нового каталога
`--output` либо `--resume`; существующий результат не перезаписывается молча.
`make check` отдельно проверяет общий проект и проверки временных границ.
Torch-тесты вынесены в `data-science/sequence-tests/`; `make check-sequence`
устанавливает зависимость и запускает их явно, без `importorskip`.

Команды реального прогона на локальном принятом snapshot (выполнены 28.09 на
незакоммиченной версии кода, см. [итог](#итог-на-реальных-данных--28092026)):

```sh
# Проверка схемы, manifest/overlay и бюджета размера, без подготовки меток/обучения.
uv run --locked --group sequence python -m infra_pulse_research.sequence preflight

# История -> отдельный приватный подготовленный набор.
uv run --locked --group sequence python -m infra_pulse_research.sequence prepare

# В отдельном терминале; используется существующий launcher и store.
make mlflow

# Все модели, два forward-fold и три seed; --tracking-uri можно опустить.
uv run --locked --group sequence python -m infra_pulse_research.sequence train \
  --tracking-uri http://127.0.0.1:5000

# Продолжение после остановки: готовые checkpoint переиспользуются при совпадении hashes.
uv run --locked --group sequence python -m infra_pulse_research.sequence train \
  --tracking-uri http://127.0.0.1:5000 --resume
```

Параметры: `--config`, `--prepared`, `--output`, `--tracking-uri`, `--resume`.
[Конфигурация](../../configs/sequence_research_v1.json) задаёт snapshot, overlay,
периоды, список архитектур, seeds, эпохи, batch, пределы памяти и устройство.
Пути config разрешаются относительно корня checkout, абсолютные тоже допустимы.
Изменения протокола сохраняются отдельным конфигом **до** открытия результатов.
Текущая конфигурация — фиксированный набор сравнения, не автоматический подбор.

CPU — проверяемый исходный режим. `device=auto` выбирает CUDA, затем MPS, затем CPU;
явно недоступное устройство или неподдержанная детерминированная операция дают
ошибку. MPS/CUDA и Linux в этом этапе не проверены. Для локального запуска на Mac
ускоритель включается только после отдельного smoke. Длительность реального
обучения пока не измерена; 30 обучений = 5 моделей × 2 fold × 3 seed.

## Данные и методика

- Единица — объект с каналами «Состояние фазы», по текущему справочнику snapshot.
  Конфликт принадлежности канала объекту останавливает подготовку. Исторических
  дат действия справочника нет; число и состав объектов сверяются до реального run.
- Текст `Неисправен` остаётся `technical_fault_state_proxy`, `alarm` не считается
  подтверждённым физическим отказом. Метки получаются общим core-детектором
  `phase_feeder_episodes`, события объединяются с W=10 мин, Q=24 ч.
- Вход сети — последние 128 сообщений объекта за 90 суток, точный текст состояния,
  `log1p` возраста записи и интервала от предыдущей записи того же канала (сутки),
  alarm и доля покрытых дней истории. Числовые напряжения не выдумываются.
  Словарь текста строится только по валидным позициям train; новые тексты — UNK.
  Padding маскируется. Порядок одновременных записей детерминирован; это не
  доказательство физического порядка сообщений. Сети пока не имеют embeddings каналов.
- Срезы ежедневно в 00:00 МСК; только записи `< cutoff`. Доступность имитируется
  временем источника: проверенной истории фактического получения нет.
  Eligibility использует год известной истории объекта, покрытый предыдущий день,
  кандидата по core и минимум одно событие за 365 дней. Будущее покрытие на выдачу
  не влияет. Между train/validation/test исключаются пересекающие границу 14-дневные
  окна метки; равенство конца окна границе допустимо.
- Будущая метка — событие в `[cutoff, cutoff+14 суток)` с каналом-кандидатом.
  При неполном покрытии **всего** будущего окна метка `-1` даже при видимом событии;
  она не участвует в обучении и знаменателе precision. Coverage означает полноту
  архива, а не исправность молчащего датчика. Пропуски overlay не превращаются в нули.
- Два fold: train 2023 → validation I полугодие 2024 → test II полугодие 2024;
  train 2023–2024 → validation I полугодие 2025 → test 07.2025–06.2026.
  Все test-периоды уже просмотрены: это диагностическое сравнение, не новый слепой holdout.
  Объекты пересекаются во времени; обобщение на новые объекты не проверяется.
- Раннее завершение — validation Logloss, максимум 20 эпох; test не выбирает эпоху.
  Сигмоидальные выходы — некалиброванные scores. Они не становятся вероятностями в UI.
  Калибровка и отдельный calibration split для неё — следующий этап при полезном кандидате.

## Честное сравнение

`static_v9_core` — счётчик событий объекта за 365 суток из core.
`catboost` — новый компактный baseline на 16 числовых признаках: счётчики 7/30/90/365,
давность, семь дневных лагов, coverage истории, длина и усечение последовательности,
день недели. Это **не** точное воспроизведение исторического v10 (там были дополнительные
категориальные и агрегатные признаки). Сети проверяют информацию последовательности
отдельно от табличных признаков; объединённая модель пока не реализована.

Каждый метод использует одни даты, eligibility и core `select_new`: максимум 10
одновременно открытых карточек, окно 14 суток, освобождение при первом событии.
В момент самого события карточка ещё открыта. Score сети переводится в ранг для
совместимости с core; минимальная историческая поддержка сохраняется в eligibility.
Методы могут выдавать разное общее число карточек из-за разного времени освобождения;
это отражено в отчёте, равенство нагрузки по общему числу не предполагается.

Отчёт содержит числители/знаменатели precision карточек и recall голов инцидентов
(gap ≥24 ч), recall новых инцидентов (нет события 14 суток), число неизвестных
карточек, среднее/максимальное число открытых на днях выдачи, концентрацию по объектам,
медианный lead, AP/ROC AUC/Brier для известных test-пар и парный недельный bootstrap
разницы со статичным списком (1000 повторов). Recall считается по покрытым головам
инцидентов в test-периоде, включая недоступные для предсказания; хвост 14 суток
оценивается без новых выдач, начало fold — с пустой очередью.

Недельные интервалы описательные: перекрытие окон и концентрация на нескольких
объектах ограничивают вывод. Bootstrap по объектам и абляции — planned.
Строгое правило censoring и определение знаменателя здесь заданы явно. Сверка состава
карточек и знаменателей с опубликованными числами v9 выполнена 29.09 на реальных данных
(`baseline_reconciliation`, см. [итог](#итог-на-реальных-данных--28092026)). Старые
опубликованные метрики не переписываются.
Отрицательный результат допустим; автоматического допуска/замены v9 нет.

## Артефакты, воспроизводимость и ограничения

Все выходы по умолчанию — в ignored `data-science/artifacts/sequence-v1/`:

- `prepared/arrays.npz`, `private.json` — тензоры, локальные ID/метки/события;
- `prepared/config.json`, `manifest.json` — конфиг, hashes входов и файлов,
  происхождение, количество unknown/eligible/truncated; manifest публикуется последним;
- `run/run.json` — переносимый агрегированный отчёт без идентификаторов объектов,
  каналов и строк телеметрии; Git SHA/dirty, code/lock/data hashes и версии библиотек;
- `run/checkpoints/` — лучшие веса, параметры архитектуры и train-словарь; вне Git.

Подготовка читает один объект за раз с ограничением числа записей; DuckDB ограничен
2 GB, итоговые тензоры — бюджетом в конфиге. При объединении частей тензоры временно
дублируются; лимит тензоров не является лимитом RSS всего Python-процесса.
Обучение идёт minibatch, подготовленные массивы остаются в RAM. Исходный snapshot
считается неизменяемым. Иная конфигурация/код/data/hash не может незаметно использовать
старый checkpoint. `--resume` возобновляет **между моделями**, а незавершённую модель
обучает заново; продолжения внутри эпохи нет.

MLflow опционален, только loopback HTTP. Вложенность runs: исследование → fold →
модель/seed. Записываются агрегаты, параметры и hashes, без датасета, ID, словаря и весов.
Без сервера остаётся тот же JSON-отчёт. Ошибка прерывает run и оставляет `status=failed`
с типом исключения; MLflow run тоже получает failed. Это исследовательские checkpoints,
не production bundle и не registry promotion.

**Planned:** Encoder–Decoder (если нужен последовательный выход по дням), Decoder-only
(если есть обоснованная задача следующего события), калибровка, абляции, доверительные
интервалы по объектам и worker parity. Эти архитектуры не реализованы
пустыми заглушками и не входят в число выполненных экспериментов.

Требования: ML-02 → config/manifest/forward-fold; ML-03 →
`tests/test_sequence_data.py`; ML-04 → replay/числители/парный bootstrap;
ML-06 → проверка hashes и roundtrip checkpoint (только research, worker planned);
ML-07 → CLI/MLflow/агрегированный отчёт. D01/D05/D06 для новых моделей остаются открытыми;
подготовка кода не закрывает научный допуск. Контракты HTTP/UI не меняются.

Использованы публичные API PyTorch:
[pack_padded_sequence](https://docs.pytorch.org/docs/stable/generated/torch.nn.utils.rnn.pack_padded_sequence.html),
[TransformerEncoder](https://docs.pytorch.org/docs/stable/generated/torch.nn.TransformerEncoder.html).
