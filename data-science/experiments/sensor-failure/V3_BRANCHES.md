## Общие правила для любой ветки

1. **Git.** Ветка от актуального `master`: `git switch -c v3-<ветка>-<имя> origin/master`.
   Коммит и PR делает исполнитель; в Git не попадают данные, веса, MLflow store и
   `data-science/artifacts/`.
2. **Данные — готовый пакет, не пересборка.** Данные в Git не входят. Владелец
   данных передаёт приватным каналом архив `sensor-failure-v1-min-<дата>.tar`
   (около 0,5 ГБ: `sensor-failure-v1/tables`, `model_labels_v2`, `features` и
   `handoff/SHA256SUMS`). Распаковать в корне репозитория:
   `tar -xf <архив> -C data-science/artifacts`. Затем проверить суммы:
   `cd data-science/artifacts && shasum -a 256 -c handoff/SHA256SUMS`. Этого
   достаточно для smoke, CV и признаков по истории эпизодов, так как подбор
   читает только метки и признаки. Полный curated snapshot v4 (около 14 ГБ) нужен
   только для признаков из сырого журнала (тревоги, «Неопределен», «Выключен»).
   Пересборка из архивов (curated v4 → overlay → таблицы → метки → признаки)
   занимает часы и на другом snapshot не воспроизводит числа v2 — ей пользоваться
   только по согласованию с аналитиком данных.
3. **Метки и признаки v2** уже в пакете из п. 2. Команды пересборки — только если
   аналитик данных попросит обновить метки:

   ```sh
   uv run --locked --group train --group research python data-science/scripts/measure_sensor_failure.py
   uv run --locked --group train --group research python data-science/scripts/measure_sensor_failure.py --reuse-tables --model-labels --model-config data-science/configs/sensor_failure_model_v2.json --labels-dir model_labels_v2
   uv run --locked --group train --group research python data-science/scripts/build_sensor_failure_features.py
   ```

4. **MLflow — у каждого свой локальный.** Сервер основного исследования
   доступен только на машине, где он запущен. Исполнитель поднимает свой
   ([MLflow](../../mlflow/README.md)): `uv run --locked --group train python
   data-science/mlflow/server.py --port 5059` и пишет в эксперимент
   `sensor-failure-v3-<ветка>`. Общий результат передаётся не через MLflow, а
   агрегированным JSON в `reports/` и разделом в документе ветки.
5. **Проверка окружения до работы.** Запустить
   `tune_sensor_failure.py --target connection_loss_gt2s --horizon 24 --smoke`
   (только CV, одна конфигурация, без MLflow; выход — `tuning_v2/smoke/`).
   Persistence не зависит от модели: средняя precision при 2 карточках/день на
   фолдах должна совпасть с v2 — 0,116 (единица A). Полный CV v2 для пары
   занимает 1–1,5 ч на 6 потоках; выбранный там `F2|c1|mean_top2|model_only`
   дал 0,166, повтор может отличаться примерно на ±0,02 из-за числа потоков
   CatBoost. Если persistence не совпала — искать причину в данных.
6. **Только фолды обучающих лет.** Оценка — годы 2023 и 2024 по
   [предрегистрации v2](../../configs/sensor_failure_tuning_v2.json). Периоды
   калибровки (2025 H1) и отложенный (2025-07…2026-06) не читать; стадию
   `final` не запускать.
7. **Предрегистрация до первого обучения.** Конфигурация
   `configs/sensor_failure_tuning_v3_<ветка>.json`: что меняется, критерий успеха
   из таблицы ниже, `thread_count`, seed 17/18/19. Показать аналитику данных до запуска.
8. **Шум.** Каждый кандидат — 3 seed, сравнение по среднему. Разница меньше
   разброса между seed — ничья.
9. **Утечки.** Всё, что видно в момент выдачи, строится только из записей до
   cutoff. Для новых признаков и меток — тест с обрезкой журнала после cutoff
   (как в [аудите утечек](LEAKAGE_AUDIT.md)) и тест на цензурирование.
10. **Сдача.**
    - Код с тестами и конфигурация.
    - Раздел в документе ветки: `TUNING_V3_<ветка>.md` или раздел в `TUNING_V3.md`.
    - Отчёт без ID объектов и каналов.
    - Фактический вывод `make check`.
    - Пометка implemented / planned; зарегистрированное событие не называть
      поломкой.

## Ветки — выбрать одну

| Ветка | Суть | Что меняется | Стоимость | Критерий (фолды 2023 и 2024) |
| --- | --- | --- | --- | --- |
| **A. Выдача в 06:00** | Список формируется в 06:00; видны события объекта с полуночи. 91% начал — после 06:00 | Сетка cutoff в `sensor_failure_target.py`, признаки на 06:00 в `sensor_failure_features.py` | 0,5–1 день, риск утечки выше среднего | P@2 выше варианта 00:00, нижняя граница недельного CI > 0; отдельно — для событий без события объекта в тот же день |
| **B. Ритм объекта** | Гипотеза «события запускают работы людей»: 54% событий с 09 до 13 ч, 72% — в рабочие часы будней | Новая группа признаков `rhythm__`: событие того же дня недели неделю назад, давность последнего события объекта, число «сессионных» дней за 30 сут, профиль объекта по дням недели | часы | F2 + ритм − F2 > 0 по P@2 на обоих фолдах (среднее по 3 seed) |
| **C. Политика выдачи** | 2 карточки в будни, 1 в выходные; статичный список прошлого года — второй ориентир рядом с persistence | `sensor_failure_evaluation.py` (политика и ориентир), без новых признаков | часы | precision выше при recall ≥ persistence − 0,02; модель выше статичного списка |
| **D. Ежечасная выдача** | Скользящее окно 24 ч, предвестники объекта за 1–6 ч (кандидаты, тревоги, «Неопределен», «Выключен», охранные датчики) | Панель карточка × час (≈ 7 млн строк за 3 года), новые метки и признаки | 1–2 дня | recall выше persistence при том же бюджете в сутки, отдельно для событий без предшествующего события объекта в тот же день |

**Распределение по умолчанию.** Участнику команды лучше взять **B**: это
независимый модуль с ясным критерием, он не трогает метки и хорошо подходит,
чтобы освоить цикл «предрегистрация → CV → MLflow → отчёт». Если есть два дня и
опыт с временными рядами — **D**. Остальные DS берут A, C и общую гигиену оценки.
Выбранную ветку фиксирует аналитик данных, чтобы две ветки не меняли одни файлы.

    00:00 (заранее заданный порог — +3 пп на обоих годах);

    таких событий, за 6 ч — у 1,1–1,7%;
  - реактивная выдача поднимает общий recall на 4–7 пп только за счёт
    продолжений уже видимой сессии (lead 1,6–3,5 ч).

  Нужна ли диспетчеру карточка «сессия на объекте продолжается» без ML —
  вопрос технологу, отдельный элемент продукта.
