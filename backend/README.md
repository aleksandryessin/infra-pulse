# Backend API

Нормативный маршрут: [API-01–API-07](../docs/REQUIREMENTS_SPEC.md#api--операционная-история),
[SEC-01–SEC-04](../docs/REQUIREMENTS_SPEC.md#sec--доступ-и-аудит) и
[OPS](../docs/REQUIREMENTS_SPEC.md#ops--переносимость-и-эксплуатация).
Перед workflow/auth закрыть D02/D03 из [реестра](../docs/REQUIREMENTS_DECISIONS.md).
В передаче: ID → интеграционные проверки БД/транзакции/audit/retry/scope;
fixture smoke не закрывает server persistence. Конкретный data-backed срез — после D01.

Workspace package `infra-pulse-backend`, import `infra_pulse_backend`. Здесь HTTP,
настройки и место для operational repositories. Canonical схемы импортируются из
`infra_pulse_core.contracts`, не копируются в backend.

Реализованы `scaffold`, `fixture`, локальный `replay` и локальный `received`. Fixture возвращает
синтетические записи; replay читает ограниченное окно принятого curated snapshot
из PostgreSQL через `/api/v1/attention` (as_of, view, offset/limit, object_id)
и `/api/v1/attention/objects`. Raw, исходный alarm, время, nullable объект и
provenance сохраняются. Предварительная policy сортирует source alarm, точные
пары тип/текст и прочие записи; это **порядок разбора**, не шкала тяжести или
принятое D01.
В ответе `/api/v1/attention` `source_alarm_count`, `watch_text_count` и
`chronological_count` суммируются в `total` выбранного `view`, времени и
серверных фильтров до пагинации. `alarm=true` учитывается только в первой
группе, даже если текст совпал с каталогом; точный текст при `alarm=false` —
во второй. Эти числа описывают сообщения, а не тяжесть или число инцидентов.
В `/api/v1/attention/objects` `attention_band` согласован со счётчиками:
`source_alarm`, если есть исходный alarm; иначе `watch_text`, если есть точный
текстовый кандидат; иначе `chronological`. Метка описывает состав выбранного
среза, а не состояние объекта.
Этот endpoint фильтрует группы до пагинации через `candidate_kind=all|alarm|text|candidate`
и возвращает `total`, `offset`, `limit` и не более 100 групп за запрос.
`text` включает группу с точным текстом при `alarm=false`, даже если в ней
есть и другие сообщения с `alarm=true`. Детализация канала по `object_id`
доступна отдельно, независимо от текущей страницы объектов.
Объектные и канальные группы также возвращают `last_source_alarm_at` и
`last_watch_text_at` по времени доступности в выбранном `as_of`/watermark.
Эти поля отделены от времени последней любой записи: поздняя «Норма» не делает
старый alarm новым и сама по себе не подтверждает устранение.
Объектные и канальные группы с кандидатами перечисляются сначала по времени
последнего кандидата; группы без кандидатов — по последней любой записи.
Поздняя обычная запись не поднимает старый кандидат над более свежим.
Это предварительный порядок навигации, не утверждённый приоритет D01.
`/api/v1/attention/{row_uid}/reviews` хранит локальные append-only
заметки с audit и выключен по умолчанию. Пагинированный
`/api/v1/review-journal` читает их вместе с неизменёнными исходными сообщениями;
необязательные `row_uid`, `object_id` и `channel_id` ограничивают журнал одной
исходной записью, объектом и/или каналом в активном stream/snapshot. Для
записей без объекта используется `object_id=__unknown__`. `total` считается
после фильтров на сервере; фильтр не закрывает тревогу и не меняет заметку.
Ответ журнала заметок содержит `review_watermark` — число зафиксированных
локальных заметок активного stream/snapshot. При перелистывании передайте это
значение обратно: новые заметки не сдвинут строки и `total` закреплённого
списка. Без параметра API показывает актуальный журнал; значение больше
текущего счётчика возвращает 422. Миграция `0010_review_position.sql`
нумерует старые заметки; новые получают позицию в одной транзакции с заметкой
и audit.
Тот же точный фильтр `row_uid` в `/api/v1/attention` возвращает исходную
карточку независимо от её текущей страницы; `view=all` включает также записи
вне предварительного списка кандидатов. Необязательный `alarm=true|false`
фильтрует именно исходное поле `alarm`, не вердикт о физической неисправности;
он работает и при выключенных локальных заметках. Фильтры действуют внутри активного
snapshot и на записи, доступные к `as_of`.
Необязательный `event_at` с часовым поясом фильтрует точное время источника;
совместно с объектом и каналом он позволяет показать все доступные к `as_of`
сообщения того же канала в этот момент, включая разные тексты и `alarm=false`.
Счётчики и пагинация относятся к этому отфильтрованному списку. Равное время
источника не устанавливает общий инцидент или причинный порядок; в received
граница `received_watermark` по-прежнему исключает ещё не принятые записи.
Новые заметки сохраняют `view_as_of`, версию policy, полосу и коды основания,
которые сервер сверяет с показанным snapshot и вычисляет из исходной записи.
В received запись заметки требует `displayed_received_watermark` из ответа
очереди: сервер проверяет, что исходная запись входит в эту границу и она не
выше числа зафиксированных импортированных строк. Запись на самой границе и
все записи до неё должны быть доступны к заявленному `view_as_of`; более
поздняя запись внутри заявленного среза отвергается. В replay поле должно быть
`null`. Сохранённая граница позволяет снова открыть показанный список после
новой партии; в заметках до миграции `0011` она неизвестна.
Синтетический PostgreSQL интеграционный тест проверяет повтор того же запроса
без второго audit, конфликт при ином payload с тем же ключом и при устаревшей
ревизии, а также откат заметки при ошибке вставки audit. После устранения ошибки
тот же запрос сохраняется и читается новым экземпляром API. Это проверка
локального пути, без авторизации диспетчера и принятого workflow.
Отдельный тест запускает два одновременных запроса к одной записи: разные
ключи дают одну ревизию и явный конфликт, одинаковый ключ возвращает один
результат обоим клиентам. В обоих случаях в БД остаётся одна audit-запись.
Очередь возвращает ревизию и время последней локальной заметки для каждой
записи на странице; заметка не удаляет её из кандидатов и не меняет raw/alarm.
Необязательный `local_note=any|present|absent` в `/api/v1/attention`
серверно ограничивает страницу по наличию заметки к исходной записи в активном
stream/snapshot. По умолчанию `any`, поэтому заметки не скрывают сообщения;
`all_records_total` остаётся числом всех исходных записей после фильтров
объекта/канала/`row_uid` и `as_of`, а `total` учитывает также `view` и
`local_note`. В replay `as_of` ограничивает исходные записи, но наличие
заметки читается из текущего локального журнала, без исторической реконструкции
его состояния. Это фильтр локальной истории, а не ACK, статус устранения или
подавление исходного alarm. В synthetic fixture заметок нет.
Ранние локальные тестовые заметки имеют пустые поля этого основания.
Это не авторизованный workflow D02/D03. В `received` тот же API читает
несколько последовательно импортированных JSON-партий одного stream. Время
`available_at` означает момент локального импорта приложением (`observed`), а не
момент доставки заказчиком. Поле `event_at` остаётся временем источника.
При конкурирующих локальных загрузках момент импорта назначается после
получения блокировки stream, вместе с порядком принятых записей; это не
измерение задержки до входной папки или проверка часов источника.
В received `GET /api/v1/capabilities` отдаёт `received_status_checked_at` —
время чтения состояния по часам PostgreSQL. Его можно сравнить с
`received_inbox_last_scan_at` для возраста последнего локального просмотра
папки даже при закреплённом списке сообщений. Это не проверка доступности
системы заказчика и не принятый порог устаревания.
Необязательный `after_received_watermark` в этом запросе возвращает число
принятых после границы записей, число среди них с исходным `alarm=true` и
число предварительных кандидатов (`alarm=true` или точная пара типа и
исходного текста), а также число различных пар указанных во входе
`object_id × channel_id` среди этих кандидатов. Это счёт групп, не
объединение сообщений или подтверждение привязки объекта.
Без нижней границы API читает только сводку stream и состояние входной папки;
он не пересчитывает все исходные записи при readiness или обычном опросе.
Счётчики относятся ко всему локальному stream, не к текущему фильтру очереди;
граница выше текущего числа записей даёт 422. `alarm=true` не означает
подтверждённую аварию или её тяжесть.
Для received `/api/v1/attention` возвращает `received_watermark` — число строк,
принятых и зафиксированных в stream на момент чтения. Повторный запрос страницы
передаёт вместе `as_of` и `received_watermark`: первый ограничивает время
доступности, второй исключает партию, начатую раньше, но зафиксированную позже.
Необязательный `after_received_watermark` оставляет только записи с большей
принятой позицией; вместе с `view=all&alarm=true` это даёт точный список новых
исходных тревог, а с `view=attention` — новых предварительных кандидатов,
включая точные текстовые совпадения при `alarm=false`. Верхняя граница сохраняется для
пагинации, нижняя не может быть выше неё; в replay обе границы received
недопустимы. Это фильтр записей, а не вывод о физическом исходе.
`/api/v1/attention/objects` и `/api/v1/attention/channels` теперь возвращают
такую же границу. При раскрытии объекта клиент передаёт оба поля из ответа
списка объектов, чтобы поздний commit не менял каналы под прежним срезом.
Для replay параметр `received_watermark` недопустим; граница больше числа
зафиксированных строк received также возвращает 422.

`GET /api/v1/attention/source-alarms?event_from=…` — окно блока «Сейчас» (F-04, обкатка
29.09): записи с `alarm=true` и временем события не раньше `event_from`, доступные на
`as_of`, с той же границей `received_watermark`. Сервер считает всё окно (`record_count`,
`object_count`, `without_object_count`) и по каждому объекту — сообщения, линии, первое и
последнее время события, последнее сообщение и `scheme_record_count`: сообщения на линиях
электропитания схемы объекта (линии раскладки, известные детектору, — то же правило, что у
`/schemes`). `objects` (до `object_limit`, по умолчанию 100) и `latest` (до `limit`, по
умолчанию 10) упорядочены по времени события, новые сверху; `/attention` сохраняет порядок
приёма: он часть политики очереди (`received_order`), а стабильность страниц даёт
`received_watermark`, не порядок. Прежде блок читал окно страницами `/attention` по времени
приёма: файл, принятый позже с более ранними событиями, вытеснял из первой тысячи сообщения
фазы объекта с открытой карточкой. Запросы идут по индексу времени события (0020): на
копии стенда (3,5 млн записей, окно 1 263) — 9 мс на три запроса.

Счётчики `/attention` (`all_records_total`, полосы) считаются одним проходом, группировкой
по полосе записи; при `local_note=present|absent` — прежние два запроса, чтобы заметки
проверялись только у записей вида. Страница `view=all` без фильтров объекта, канала,
записи, alarm и времени сливает три упорядоченных диапазона индекса очереди (`alarm` =
true, false, не передан) вместо сортировки всей области. На копии стенда `view=all` без
фильтров — 0,84 с вместо 2,0 с; `view=attention` без фильтров — 1,8 с вместо 2,2 с (порядок
полос по-прежнему сортирует всю область).
Миграция `0009_received_position.sql` нумерует уже принятые строки и требует
позицию для каждой новой received-записи. Перед запуском обновлённого API на
существующей БД выполните из корня:

```sh
INFRA_DB_DSN="$INFRA_RECEIVED_DSN" uv run --locked python backend/scripts/migrate_operational_db.py
```

Локальный loader также применяет миграции при импорте. `received_watermark`
фиксирует исходные сообщения, а `review_watermark` отдельно фиксирует
страницы локального журнала заметок.
Интеграционный тест `test_candidate_lanes_keep_received_watermark_after_late_commit`
проверяет оба вида кандидатов при позднем commit с временем доступности внутри
старого `as_of`: закреплённые страницы остаются прежними, а запрос без границы
видит новые записи. Это проверка локального read-path, не customer live.
`GET /api/v1/attention/channels?object_id=...&as_of=...` даёт пагинированные
группы `объект × указанная система × канал` с числом исходных записей и моментом
последней доступной группы. Необязательный `channel_id` выбирает точный канал
внутри объекта. `object_id=__unknown__` выбирает записи без
привязки. Если в последней группе несколько сообщений или её время источника
старше уже виденного, ответ содержит явные признаки неоднозначности. Полная
история канала доступна через `/api/v1/attention?object_id=...&channel_id=...&view=all`.
Поле `multiple_object_ids_seen` у канала показывает, встречается ли тот же
`channel_id` с иным `object_id` среди доступных к `as_of` записей активного
stream/snapshot; `NULL` также считается отдельной привязкой. Это проверка
согласованности входа, не автоматическое исправление mapping и не физический
вывод о перемещении датчика.
`view=all` перечисляет все исходные записи по времени доступности (сначала
новые), независимо от `alarm`/каталога кандидатов; `view=attention` сохраняет
предварительный порядок проверки. Время доступности replay симулировано.
Исторический replay дополнительно проверяет hash `channels.parquet` из accepted
manifest и загружает текущий справочник каналов в отдельную таблицу.
`/api/v1/attention/coverage/objects?as_of=...` и
`/api/v1/attention/coverage/channels?as_of=...&object_id=...` показывают,
какие каналы справочника имели запись в ограниченном replay-окне, а какие нет.
Второй маршрут пагинирован. Текущая привязка справочника не является доказанной
исторической топологией; отсутствие записи не означает норму или неисправность.
Каналы вне справочника остаются в обычной очереди и объектных группах. В
`received` этот reference endpoint отвечает 503: подтверждённого roster для
локального входного формата нет.
Это навигация по сообщениям, а не проекция физического текущего состояния.
HTTP не загружает research package, MLflow или библиотеки обучения. Inference и
live не реализованы.

## Прогноз «обесточивание фидеров объекта» из PostgreSQL (B2, 27.09.2026)

Статус — **implemented** на синтетике и на истории фазы в одноразовой локальной БД;
на стенде не запускался. Требования: API-01/API-07 (публикация, повтор), ML-05
(«доля k из n» без слова «вероятность»), UI-06 (пикет из названия, 10 м на пикет);
постановка — `sensor_failure_final_v9.json`, `prod_phase`.

- **Пересчёт.** `operations.forecast_publish.recompute(connection, *, data_as_of,
  import_id)` вызывает воркер B1 внутри своей транзакции после загрузки журнала. Возвращает
  `PublishResult(generation, new_card_ids, released_card_ids, run_id, timings)`. Один вызов —
  один run с `generation + 1`:
  - `detect` — core-детектор (`infra_pulse_core.features.phase_feeder_episodes`) читает новые
    записи «Состояние фазы» после `received_position` детектора и переносит состояние канала.
    Запись раньше watermark канала пересобирает этот канал из истории;
  - `score` — каждый cutoff 00:00 МСК после прошлого и не позже `data_as_of`: кандидаты,
    причинная допустимость, список 365 сут, шаг списка 14 сут / K = 10;
  - `publish` — неизменяемые снимки карточек (триггер БД), исходы и события окна, журнал
    жизненного цикла, run.

  Scope — `import_files.target_namespace/target_stream` загрузки, иначе received-настройки.
- **Таблицы** — миграция `0013_forecast_publication.sql`, повторное применение безопасно:
  - детектор: состояние, эпизоды, кандидаты, события (цепочки W = 10 мин);
  - дни покрытия, `forecast_channel_layout` (пикет, вид фидера, ориентир, версия словаря);
  - runs, cutoffs, карточки (JSON контракта), исходы, события окна.

  Все таблицы привязаны к `(namespace_id, snapshot_id)`; внешних ключей на B1/B3 нет.
- **Чтение** — `api/forecast_db.py`: все маршруты `api/forecasts.py` и `/schemes`.
  - `as_of` по умолчанию равен `data_as_of` последнего run и не бывает позже него. Карточка
    видна с cutoff, освобождение — с момента события, исход — с момента разрешения.
  - Смена `generation` делает cursor списка устаревшим (409); cursor журнала закреплён
    `journal_watermark` и границей решений `records_as_of`.
  - `/forecast-journal/quality` — `r_incident` и `r_strict` (`definition_version`
    `sensor-failure-final-v9`) и «k из n» по карточкам. Это иллюстрация на истории
    (`demo_period`), не метрика.
  - `/forecast-state` называет сутки без данных перед последней выдачей: `no_data_from` …
    `no_data_to` (даты МСК; P1-2 репетиции 29.09.2026). Это сутки после последнего дня с
    данными (`forecast_coverage_days`: `covered` и не день политики исключений) до дня перед
    последним cutoff; выдачи на них — без карточек. Если день перед cutoff с данными — оба
    поля `null`. Тест — `test_state_names_the_days_without_data_before_the_latest_cutoff`.
  - **Кэш чтения** (`api/read_cache.py`, OPS-01, 28.09.2026). Ключ — публикация,
    которую видит транзакция запроса: строка подключения без пароля, область,
    `generation`, `data_as_of`, `created_at` run. К ключу добавляются параметры запроса.
    - Хранит карточки с исходами (без JSON), ответы `/forecasts`, сводки журнала,

    - Новая публикация читается сразу. Решения и результаты проверки журнал читает на
      каждом запросе.

      списком. «Обесточен» событий страницы журнала — одним запросом.
    - Кэш — в памяти процесса. Поздняя исходная запись без новой публикации попадёт в
      тревоги схемы не позже чем через TTL.

      `/forecast-state` и `/notifications` требуют индекс по `event_at` (миграция 0020).

- **Решение в журнале (B3, исправлено 29.09.2026 по аудиту Б-1).** У журнала две оси
  времени. `as_of` — момент данных: карточки, исходы и события окна не позже него (не

  журнала несёт последние из них, сохранённые не позже `records_as_of`. Без `as_of` в
  запросе это момент чтения, поэтому решение, принятое на стенде с историей до

  `decision_code` рекомендации карточки остаётся `None`.

Локальный replay запускается отдельно от API; исходный curated остаётся вне Git:

```sh
# PostgreSQL должен быть запущен, а snapshot — accepted и доступен локально.
export INFRA_REPLAY_DSN='postgresql://USER@127.0.0.1:5432/infra_pulse'
uv run --locked --group platform --group data python backend/scripts/load_attention_replay.py \
  --snapshot /absolute/path/to/accepted-snapshot --month 2025-06 \
  --start 2025-06-01T00:00:00Z --end 2025-06-01T01:00:00Z
# Возьмите snapshot_id из JSON-отчёта загрузчика.
INFRA_MODE=replay INFRA_DB_DSN="$INFRA_REPLAY_DSN" \
  INFRA_REPLAY_SNAPSHOT_ID='<snapshot_id>' INFRA_ENABLE_LOCAL_REVIEWS=true \
  uv run --locked uvicorn infra_pulse_backend.api.app:app --host 127.0.0.1 --port 8000
```

На серверном стенде тот же loader, миграции и received watcher запускаются в
контейнерах target `ops` с read-only каталогом данных:
[runbook стенда](../deploy/README.md#8-реальные-данные-replay).

После загрузки ограниченного replay-окна можно сверить **все** страницы API с
каждым `row_uid` принятого месячного Parquet и содержание каждой исходной
карточки полного списка: точный текст, исходный `alarm`, объект, канал, типы,
nullable число, время, provenance и флаги качества. Отдельно сверяются
полный список,
исходных `alarm=true` и точных текстовых кандидатов. Скрипт также сверяет
с исходным Parquet состав и счётчики объектных групп и групп каналов для
`all|alarm|text|candidate` до страниц; выводит только агрегаты и hashes.
Например, для пиковых пяти минут 06.11.2025 из
[локальной QA](../docs/OPERATIONS.md#пиковый-пятиминутный-replay-и-сквозной-путь-25092026):

```sh
uv run --locked --group platform --group data python \
  backend/scripts/verify_replay_api.py \
  --snapshot data-science/artifacts/curated-except-2021 --month 2025-11 \
  --start 2025-11-06T08:30:00Z --end 2025-11-06T08:35:00Z \
  --base-url http://127.0.0.1:8000
```

Это проверка bounded historical replay с симулированной доступностью, не
проверка customer live, разрешённого правила D01 или эксплуатационного SLA.

Загрузчик проверяет hash выбранного Parquet, сверяет source/loaded row и alarm
IDs и безопасен при повторном запуске. `available_at` для истории симулируется
равным `event_at`: фактическое время поступления неизвестно. Локальные заметки
не следует включать на публичном сервере без аутентификации и принятого D02/D03.

Локальный вход новых партий — **кандидат формата**, пока D07/D14 открыты. JSON
содержит `batch_id` и `records` (1–5000); у каждой записи обязательны уникальный
в партии `source_record_id`, `channel_id`, точный `value_raw`, boolean `alarm` и
`event_at` со смещением зоны. Необязательны `source_event_id`, `object_id`,
`sensor_type`, `system_type`, `value_numeric`, `reference_version`. Лимит файла
5 MiB; неизвестные поля, дубликаты ID, неоднозначный alarm и время без зоны
отклоняются. Например, только с синтетическими значениями:

```json
{"batch_id":"sample-001","records":[{"source_record_id":"r1","channel_id":"sample-gas-1","object_id":"sample-object","sensor_type":"Газовый датчик","value_raw":"Обнаружен газ","alarm":false,"event_at":"2026-09-24T12:00:00+03:00"}]}
```

```sh
export INFRA_RECEIVED_DSN='postgresql://USER@127.0.0.1:5432/infra_pulse'
uv run --locked python backend/scripts/load_received_batch.py \
  --input /absolute/path/to/local-batch.json --stream local-session-1
INFRA_MODE=received INFRA_DB_DSN="$INFRA_RECEIVED_DSN" \
  INFRA_RECEIVED_STREAM_ID=local-session-1 INFRA_ENABLE_LOCAL_REVIEWS=true \
  uv run --locked uvicorn infra_pulse_backend.api.app:app --host 127.0.0.1 --port 8000
```

Вместо однократного `--input` можно в отдельном терминале следить за папкой:

```sh
export INFRA_RECEIVED_DSN='postgresql://USER@127.0.0.1:5432/infra_pulse'
uv run --locked python backend/scripts/load_received_batch.py \
  --directory /absolute/path/to/inbox --stream local-session-1 --watch
```

`--namespace` по умолчанию `local-received`; он должен совпасть с
`INFRA_RECEIVED_NAMESPACE` при переопределении. Повтор тех же байтов и `batch_id`
не создаёт записей, другой файл с тем же `batch_id` отклоняется. Импорт
транзакционный; source hash и строковые значения сохраняются. Входной `object_id`
помечен как неподтверждённая привязка. Это не коннектор заказчика, не
авторизованная смена и не мониторинг доступности канала между партиями.
Папку можно просмотреть однократно без `--watch`; опрос по умолчанию раз в 5 с,
не более 100 новых/изменённых файлов за проход. Отправитель пишет временный файл
без расширения `.json` и атомарно переименовывает его после записи. Невалидный
или конфликтующий файл остаётся в папке; счётчик отказов и время последнего
просмотра доступны через `/api/v1/capabilities`. После исправления файл с тем же
именем импортируется при следующем изменении; удаление файла снимает его ошибку.
Содержимое и текст ошибки API не раскрывает. После перезапуска watcher повторно
просматривает папку, а batch ID и hash защищают от дублей. Просроченный момент
просмотра означает, что своевременность приёма не подтверждена.

### Воспроизводимый локальный сценарий очереди

Для быстрого сквозного просмотра без уже запущенной БД из корня репозитория:

```sh
uv run --locked python backend/scripts/demo_received_local.py
```

Нужны локальные `initdb`, `pg_ctl`, `uv` и `npm` в PATH и заранее выполненные
`uv sync --locked` и `npm --prefix frontend ci`. Скрипт создаёт временную БД,
запускает watcher временной папки, атомарно помещает в неё первый вымышленный
fixture, затем запускает API/UI на `127.0.0.1` и печатает адрес очереди.
Для второй партии он печатает команду копирования другого вымышленного fixture
в ту же папку: после импорта видны новый объект, исходная запись и кандидат.
По Ctrl+C скрипт останавливает процессы и удаляет БД с папкой. Порты API/UI можно
задать через `--api-port` и `--web-port`. Это синтетическая демонстрация, без
внешнего источника, авторизации и доказательства SLA.

Сохранность исходной записи, локального решения и audit после остановки и
повторного запуска самой PostgreSQL проверяется отдельно:

```sh
UV_OFFLINE=1 uv run --locked python backend/scripts/verify_received_restart.py
```

Нужны `initdb` и `pg_ctl` в PATH. Скрипт создаёт временную БД только на
`127.0.0.1`, использует вымышленные записи и удаляет БД после проверки.
Во время остановки БД он требует HTTP 503 от readiness и очереди, после
запуска — HTTP 200 от readiness и сохранённые записи/решение.
Это проверка локального restart, не резервной копии или восстановления на
другом сервере (OPS-02/D09).

В [`fixtures/received-batch.synthetic.json`](fixtures/received-batch.synthetic.json)
и [`fixtures/received-batch-followup.synthetic.json`](fixtures/received-batch-followup.synthetic.json)
лежат только вымышленные объекты, каналы и сообщения. Для отдельной ручной
проверки watcher на **пустой локальной БД** запустите показанную выше команду
`load_received_batch.py --directory ... --watch`, затем атомарно передайте
первый файл в выбранную папку:

```sh
cp backend/fixtures/received-batch.synthetic.json /absolute/path/to/inbox/demo.part
mv /absolute/path/to/inbox/demo.part /absolute/path/to/inbox/demo.json
```

Watcher должен вывести `status=imported`, `rows=3`; при повторе того же batch
новых строк не появится. Запустите API в `INFRA_MODE=received` с тем же stream,
а frontend по [инструкции](../frontend/README.md) с `VITE_DATA_MODE=received`.
В `/queue` ожидаются 3 исходные записи и 2 предварительных кандидата:
`alarm=true` у насоса и точная пара тип/текст при `alarm=false` у вентилятора.
«Норма» доступна во всех исходных; она не доказывает исправность канала.
Карточка насоса ведёт к объекту и каналу в `/map`; привязка из входного файла
остаётся неподтверждённой. При включённых локальных заметках сохраните тестовые
действие, результат и основание, затем проверьте их в `/journal` после reload.
Это демонстрация локального пути приёма, не подключение к заказчику, авторизация
диспетчера или доказательство эксплуатационного SLA.

Физическое имя общей таблицы scope содержит `replay` по совместимости с первым
локальным режимом; `scope_kind` различает режимы.

### Сверка синтетического многообъектного received burst

Сквозная сверка пикового **синтетического** многообъектного импорта запускается
только с пустой одноразовой PostgreSQL и локальным received API, настроенным на
тот же stream и namespace `synthetic-burst`:

```sh
INFRA_RECEIVED_DSN=postgresql://USER@127.0.0.1:PORT/DB \
  uv run --locked python backend/scripts/verify_received_burst.py \
  --stream synthetic-burst-local-1 --base-url http://127.0.0.1:8000
```

Скрипт проверяет 3 705 исходных строк, все страницы API и объектные суммы.
Для полного списка он также сравнивает каждую карточку с исходной JSON-партией:
точный текст, `alarm`, объект/канал/типы, время источника и локального приёма,
provenance и флаги качества. Затем он импортирует ещё одну партию, проверяет
содержание её тревожного сообщения и неизменность закреплённой очереди.
Он откажет на непустой БД или при нелокальном адресе. Метод и фактический
результат — в [OPERATIONS](../docs/OPERATIONS.md#синтетический-многообъектный-received-burst-25092026).
`GET /api/v1/attention/channels` принимает необязательный
`candidate_kind=all|alarm|text|candidate`. Он фильтрует группы каналов
**до** `limit/offset`, сохраняя агрегаты каждой группы по всем её исходным
записям выбранного `as_of` и `received_watermark`. `text` означает точную
пару типа и исходного текста при `alarm=false`, а не диагноз или приоритет.
`tests/test_component_boundaries.py` проверяет импортную границу и API artifacts;
CI дополнительно запускает API в минимальном окружении. Вспомогательные
проверки API не импортируют DuckDB; полная сверка с Parquet требует `--group data`.

`backend/Dockerfile` собирается с контекстом корня: `docker compose build api`.
Research manifest нужен resolver-у workspace; research source/data не копируются
в образ. Frontend — отдельный компонент. Прогноз пересчитывает worker этого пакета через `infra_pulse_core`.
Runtime пути `var/data`, `var/models` пока не используются scaffold/fixture.

### Вход, роли, решения и audit (B3, 27.09.2026)

Требования SEC-02, SEC-03, API-03, API-04; SEC-01 (территориальные scopes) — planned.
Эксплуатация публичного стенда — [deploy/README.md](../deploy/README.md#11-публичный-доступ).

- **Режимы.** `dev_stub` (по умолчанию, только локально и за туннелем) — все запросы
  от локального оператора. `ldap` — сессия обязательна для всех маршрутов, кроме
  `/health/*`, `/auth/login` и `/auth/logout`. Документация API — Swagger UI `/api/docs`
  и схема `/api/openapi.json` ([`api/docs.py`](src/infra_pulse_backend/api/docs.py)) —
  отключена, пока не задан `INFRA_PUBLIC_DOCS=true` (в `dev_stub` включена всегда).
  Включение открывает только документацию: маршруты по-прежнему требуют сессию или токен
  (`test_rbac_matrix.py`), страница — без inline-скриптов и CDN (`test_api_docs.py`).
  Корневых `/docs`, `/redoc`, `/openapi.json` и ReDoc нет.
- **Код.** [`auth/ldap.py`](src/infra_pulse_backend/auth/ldap.py) — bind от имени
  пользователя через `ldap3`, группы `dispatcher`/`analyst`/`admin` → роли.
  [`auth/sessions.py`](src/infra_pulse_backend/auth/sessions.py) — серверные сессии.
  [`auth/throttle.py`](src/infra_pulse_backend/auth/throttle.py) — ограничение
  неудачных входов. [`api/auth_deps.py`](src/infra_pulse_backend/api/auth_deps.py) —
  `current_actor` и `require_permission`, сигнатуры C0 сохранены.
- **Права** — `PERMISSIONS` из contract: `read` — любая роль, `decide` — dispatcher и
  admin, `import` — admin, `research` («Исследование» и P/R журнала, C0.1) — analyst и
  admin. Нет сессии → 401, чужая роль → 403. Матрица по всем маршрутам —
  `tests/test_rbac_matrix.py`; второй карты прав нет.
- **Для SPA.** Вход — `POST /api/v1/auth/login` с заголовком `X-CSRF-Token`; до входа
  подходит любое непустое значение. Ответ ставит две cookie:
  `__Host-infrapulse-session` (HttpOnly) и `__Host-infrapulse-csrf` (читается SPA).
  Обе — Secure, SameSite=Lax, со сроком сессии. Каждый POST
  передаёт значение `__Host-infrapulse-csrf` в `X-CSRF-Token`. Коды: 401
  `not_authenticated`/`session_expired`/`invalid_credentials`, 403
  `forbidden_role`/`no_role`/`csrf_failed`/`csrf_header_required`, 429
  `login_throttled` с `Retry-After`, 503 `directory_unavailable`/`auth_storage_*`.
- **Решение** ([`storage/decisions_pg.py`](src/infra_pulse_backend/storage/decisions_pg.py)):
  один POST — одна транзакция под advisory lock карточки. В ней ревизия решения
  R1–R7 с причиной `R<n>.<m>` той же группы (иначе 422 `reason_code_mismatch`),
  `verification_methods` и «кому и когда сообщено» (`notified_to`/`notified_at`, оба
  или ни одного; время позже решения → 422 `notified_after_decision`, время решения —
  часы БД в транзакции). Для R3/R4 — черновик `not_sent`. Там же `audit_events`
  (`decision.created` с получателем и временем уведомления, `draft.created`). Автор
  берётся из сессии, тело его не задаёт.
  Повтор с тем же `idempotency_key` возвращает сохранённое без новых строк. Тот же ключ
  с другим телом → 409 `idempotency_key_reused`; устаревший `expected_revision` → 409
  `decision_revision_conflict`. `GET .../decisions` отдаёт ревизии с авторами, новые
  первыми. `latest_decisions(..., as_of=)` — последнее решение по карточкам не позже
  `as_of`; его читает журнал прогнозов B2.
- **Audit** ([`storage/audit_pg.py`](src/infra_pulse_backend/storage/audit_pg.py)):
  `record_audit_event(connection, AuditEvent(...))` пишет в транзакции вызывающего.
  Поля: actor, роль, время, действие, цель, request id, адрес, детали без секретов.
  Сейчас пишутся `auth.login`, `auth.login_failed`, `auth.login_denied`, `auth.logout`,
  решения, черновики и загрузки файлов (`import.uploaded`, B1 — в транзакции загрузки).
  Таблица пополняется только вставкой: UPDATE и DELETE отклоняет триггер
  (так же для `forecast_decisions`). Заметки attention берут автора из сессии.
- **Настройки** (`INFRA_`): `LDAP_URL`, `LDAP_BASE_DN`, `LDAP_TIMEOUT_SECONDS`,
  `SESSION_TTL_MINUTES` (480), `LOGIN_MAX_FAILURES` (5), `LOGIN_WINDOW_SECONDS` (300),
  `PUBLIC_DOCS` (false). Сессиям нужен `INFRA_DB_DSN` и миграция 0014.
- **Тесты.** `tests/test_rbac_matrix.py` и `tests/test_auth_ldap.py` работают без БД

  Bind к настоящему lldap проверяет smoke `remote-deploy.sh --public`; локально он
  не выполнялся.

### Уведомления и отчёты для руководства (N1, R1, 27.09.2026)

Статус: **implemented** для fixture и для чтения из PostgreSQL в `replay`/`received`;
в `replay`/`received` оба маршрута опираются на опубликованный прогноз B2
(`forecast_db.forecast_state` и `forecast_journal`). Без DSN или scope они отвечают 503
`forecast_not_implemented`, до первой публикации — 503 `forecast_not_published`;
`scaffold` — 503 `notifications_not_implemented` / `reports_not_implemented`.
Fixture JSON — синтетика C0.2 (`api/product_fixture.py`); в нём пустой месяц — пустые
списки, а решения — только встреченные коды. Сборка по БД отдаёт нулевую строку на
каждую опубликованную цель и все коды R1–R7. Колокольчик F1 пока считает на клиенте;
переключение на этот маршрут — отдельный шаг фронтенда.
ТЗ §10 и §8 (опционально); UI-03 (встроенные уведомления), OUT-03 (без звука и внешних
каналов), SEC-03 (права на сервере).

**Уведомления** — `GET /api/v1/notifications?since=<ISO со смещением>`, право `read`
(у `integration` его нет), `Cache-Control: no-store`. Ответ `NotificationSummary`:
- `new_cards` — оценённые карточки, опубликованные в `(since, as_of]`, из журнала
  прогнозов; `critical_alarms` — **строки** исходных записей по политике ниже (свёрнутая
  серия или повторы одного канала за час — одна строка). Счётчики точные и не смешиваются,
  `items` — до 50, `truncated` — есть ли ещё. В список сначала отбираются «Обнаружен газ»
  вне серии, затем самые новые; порядок в ответе — новые первыми (правило contract);
- часы стенда — опубликованное состояние B2: записи не позже `data_as_of` по времени
  события; `as_of` ответа — на шкале данных: `data_as_of` или время публикации
  последней карточки, если оно позже (`operations.notifications.settle_on_cards`).
  `published_at` состояния B2 — время запуска пересчёта по часам сервера; на
  исторических данных оно на год позже данных и окно не продлевает. `since` — тоже
  время данных: берите `as_of` прошлого ответа или `data_as_of` из `/forecast-state`.
  Доступность записи:
  в `replay` — не позже `data_as_of` (смоделированная), в `received` — не позже
  текущего времени (загрузка истории приходит сейчас с прошлыми событиями);
- `since` обязателен и со смещением; окно не больше 7 сут. Ошибки 422:
  `aware_since_required`, `since_after_as_of`, `since_window_too_long`. 503:
  `forecast_not_implemented`, `forecast_not_published`, `observations_not_configured`,
  `observation_scope_not_loaded`, `notifications_storage_unavailable`.

Политика — версионированный JSON в коде
([`operations/notifications.py`](src/infra_pulse_backend/operations/notifications.py),
`critical-alarms-v1`, согласована на внутренней приёмке и технологом эксплуатации;
`policy_confirmed = false` до согласования с заказчиком). Нагрузка на 2023–2024 (729 суток,
пересчёт аналитика данных 29.09 кодом этого модуля — `CRITICAL_PAIRS`, `with_power_context`,
`alarm_rows`): записей-кандидатов v0 — p90 367 в сутки; строк v1 — медиана 4 в сутки,
p90 32, p95 61. Точный тип датчика и дословный текст, исходный `alarm` не
требуется. Ничего не скрывается: свёрнутая строка называет число записей и хранит их ID.
- «Датчик дыма» — «Обнаружен дым»; «Тепловой датчик» — «Не замкнут»; «Ручной
  извещатель» — «Не замкнут», «Рычаг сдернут». **(б)** ≥ 5 каналов этих извещателей
  объекта за 10 мин в будни 07:00–19:00 МСК — одна строка «Похоже на ППР или ТО:
  N извещателей — сверить с графиком» (ППР и ТО — слова заказчика, ответ 28.09; графика
  работ в сервисе нет). Ночные серии и серии в выходные не помечаются: каждая запись — своя
  строка.
- **(в)** «Газовый датчик» — «Обнаружен газ» при любом `alarm`. ≥ 5 каналов объекта за
  10 мин (в любое время) — одна строка «Похоже на ППР или ТО: N газоанализаторов — сверить
  с графиком»; одиночная запись отбирается в список первой.
- **(а)** «Состояние насоса» — «Затоплен», только если на объекте (без объекта — на
  канале) в ±10 мин нет «Обесточен» или «Неисправен» не позже `data_as_of`; иначе это
  подпись обесточивания (99%) и не критическая запись.
- **(г)** «Датчик затопления» — «Не замкнут»: дребезг — одна строка на канал и
  календарный час МСК с числом записей.
- **Повторы (29.09, обкатка на данных июня 2026):** вне серии записи одного канала с тем же
  текстом за календарный час МСК — одна строка `chatter` «Датчик дыма: «Обнаружен дым» ×5»
  (интервал — `first_at`–`at` и в `rule_text`; интерфейс пишет под строкой «с 16:30 по
  16:56») для всех правил, как (г); одиночная запись остаётся `single`. Это
  отображение: отбор не меняется, строка хранит все записи; «Обнаружен газ» вне серии
  по-прежнему первый. Офлайн-расчёт функциями модуля на данных копии стенда
  (`bell-seed`, вне Git): окно до 30.06.2026 23:53:40 МСК — 17 строк вместо 33
  (22 из 33 давали четыре дымовых извещателя с повторами), июнь — 492 строки вместо 1 319
  (контекст питания без линий фазы). Нагрузка 2023–2024 выше посчитана до этой свёртки.

Тексты — лексемы журнала по типам (технолог; справочник состояний заказчика
частичный и противоречит журналу). В v1 не отбираются: двери, люки, «Неисправен»,
температура. По классификации заказчика (ответ 28.09) авария — угроза жизни людей: пожар,
затопление, газ, проникновение нарушителя, аномальная температура; правила для охраны и
температуры — следующий шаг (`critical-alarms-v2`), до него пробел назван в подписи.
Серия считается и через границу `since` (чтение с запасом 1 ч).
Попадание в сессию ТО не проверяется: `maintenance_check = "not_applied"`
до маски ТО (B4). Звука, внешних каналов и стиля «критично» в данных нет.
Подпись для заказчика (`NOTIFICATION_CAPTION`, в JSON политики; fixture — с префиксом
«Синтетика.»): «Колокольчик — сообщения источника, которые по тексту могут означать аварию,
то есть угрозу жизни людей (классификация заказчика, 28.09). Сейчас в списке пожар, газ и
затопление; охранные сработки и аномальная температура пока не входят. Каждое сообщение
проверяют диспетчер и дежурный инженер: это не подтверждённая авария. Серии, похожие на ППР
или ТО, показываются одной строкой и не скрываются. Правило отбора с заказчиком пока не
согласовано».
Состав свёрнутой строки — `members` (до 50 новейших записей, старые первыми): ID записи,
`channel_id`, `channel_name` (из раскладки каналов `forecast_channel_layout`, как в
`/attention`; канала нет в раскладке — `null`, QA 29.09), время и текст; «газ первым» —
`priority`. Все ID записей строки — в `AlarmRow.member_ids` на сервере.

**Отчёты** — право `report` (analyst, admin), `Cache-Control: no-store`:
- `GET /api/v1/reports/monthly?month=YYYY-MM` — `MonthlyReport`;
- `GET /api/v1/reports/monthly.xlsx?month=` — те же числа (XLSX строится из того же
  объекта) на листах «Карточки», «Решения», «Объекты», «Тревожные сообщения по типам»,
  «Условия»;
- `GET /api/v1/reports/journal.xlsx?issued_from=&issued_to=` — журнал выданных
  прогнозов за ≤ 93 сут (иначе 422 `journal_period_exceeds_93_days`): выдано, объект,
  строка события, факт, время события, решение и причина, роль автора, кому и когда
  сообщено. Новые записи сверху.

`Content-Disposition: attachment; filename="infrapulse-…xlsx"`. Ошибки: 422
`invalid_month`/нарушение шаблона месяца, `issued_range_reversed`,
`journal_period_exceeds_93_days`; 503 — как у уведомлений, плюс
`reports_storage_unavailable`. PDF — печать страницы отчёта из браузера, серверных
зависимостей нет.

Правила сводки ([`operations/reports.py`](src/infra_pulse_backend/operations/reports.py)):
- карточки месяца — оценённые, выданные в месяце по дате выдачи (МСК);
- каждая учтена один раз: «снята по событию», «без события», «неизвестно» или
  «открыто» (исхода ещё нет), сумма — «выдано»;
- решения — последняя ревизия по карточкам месяца, все коды R1–R7 с нулями;
- топ-10 объектов — по карточкам, снятым по событию и исходным тревогам;
- тревоги по типам — исходные записи с `alarm=true` в месяце не позже `data_as_of`
  ([`storage/reports_pg.py`](src/infra_pulse_backend/storage/reports_pg.py));
- пустой месяц — нули по опубликованным целям.

XLSX — `openpyxl` в write-only режиме:
- заголовки на русском, даты — МСК без часового пояса, только значения;
- текст пишется текстом: значение с «=» не станет формулой, управляющие символы
  показываются как `\xNN`;
- журнал пишется страницами по 100 записей, память от числа строк не растёт.

В файлах нет ID сессий, паролей и текста заметок. Автор решения указан ролью, причина
решения — дословно. Это счётчики событий, не метрика качества; P и R — только в
«Исследовании».

**Проверки.** `tests/test_notifications.py` и `tests/test_reports.py` работают без БД.
`tests/test_notifications_db.py` и `tests/test_reports_db.py` входят в `make check-db`;
в них прогноз B2 подменён синтетическим fixture, наблюдения синтетические.

Правила v1 (а)–(г) проверяются на синтетике в `tests/test_notifications.py` (по тесту

### Загрузка CSV и ingestion-worker (B1)

Статус на 27.09.2026 — **implemented** для пути «файл → PostgreSQL → пересчёт →
статус». Воркер находит `infra_pulse_backend.operations.forecast_publish.recompute`
(B2) через `RECOMPUTE_MODULE` и после загрузки журнала публикует карточки
([прогноз из PostgreSQL](#прогноз-обесточивание-фидеров-объекта-из-postgresql-b2-27092026));
без этого модуля он вызывает локальную заглушку, и загрузка остаётся в `imported`.
Требования: DATA-02, DATA-03 (accounting загрузки), DATA-04, API-07 (часть ingestion),
SEC-03 (audit загрузки). Автор загрузки берётся из сессии (`auth_deps`) и пишется в
`import_files.uploaded_by`, а событие `import.uploaded` (роль, request id, адрес,
SHA-256, формат, размер) — в `audit_events` той же транзакцией, что `import_files` и
`jobs` (`ingestion/imports_pg.create_import`). Ошибка audit откатывает загрузку
целиком, сохранённая копия файла удаляется, ответ 503 `imports_storage_unavailable`.

**Путь.** `POST /api/v1/imports` (роль с правом `import`, multipart `file` и `format`:
`journal_csv` | `reference_channels_csv` | `reference_objects_csv` | `reference_states_csv`;
в режиме `ldap` — с `X-CSRF-Token`) потоково пишет файл в `INFRA_UPLOAD_DIR` (временное
имя, fsync, rename), считает SHA-256, в одной транзакции создаёт `import_files`
(`queued`), `jobs` и запись audit, делает `NOTIFY` и отвечает 202. Больше 50 MB — 413
`file_too_large`, файл не сохраняется. Всё остальное
делает отдельный процесс `python -m infra_pulse_backend.worker` (тот же образ, stage
`worker`): разбор, запись, вызов пересчёта, статус. `GET /api/v1/imports` (новые
сначала, cursor — порядковый номер загрузки) и `GET /api/v1/imports/{id}` читают отчёт:
строки всего/принято/дубли/quarantine, неизвестные каналы, период, версия справочника,
тайминги этапов (`store`, `parse`, `load`, `publish`), до 20 примеров quarantine.
Столбцы справочников и журнала, синтетические файлы `docs/examples/` и порядок загрузки в
локальном Compose — [INTEGRATION_API](../docs/INTEGRATION_API.md#форматы-файлов),
[сквозная проверка](../docs/INTEGRATION_API.md#сквозная-проверка-за-5-минут).

**Статусы.** `queued → parsing → imported → recomputing → published`, либо `duplicate`
(тот же SHA и формат уже приняты; `duplicate_of`, новых строк 0, копия файла удаляется)
либо `failed` с `error_code`: `bad_header`, `bad_encoding`, `no_valid_rows`,
`reference_missing` (журнал до первого справочника каналов), `recompute_failed`
(строки остаются загруженными), `internal_error`. Справочник после записи сразу
`published`. Журнал после пересчёта — `published` с `forecast_generation`,
`new_card_ids` и `released_card_ids`; если пересчёт не вызывался (заглушка, нет
принятых журналов) — остаётся `imported`.

**Разбор** (`ingestion/journal_csv.py`, правила curated ETL `journal-curated-v4`):
- принимаются пример организаторов (кавычки, `true`/`false`) и архив (`t`/`f` без
  кавычек), UTF-8 с BOM или без, LF/CRLF; записи — по CSV-парсеру, не по строкам;
- `значение_датчика` сохраняется дословно в `value_raw`; `value_numeric` — только для
  десятичного числа с точкой (`1,5` и слова остаются текстом, NULL в числе);
- `дата` `YYYY-MM-DD` + `время` `HH:MM:SS[.ffffff]` — МСК с фиксированным UTC+03:00;
  исходный текст — `event_local_raw`;
- 1970-01-01 03:00:00/01 или значение `01.01.1970 03:00:00/01` — флаг
  `is_epoch_placeholder` в `quality_flags`, значение не переписывается;
- `ид_события` — текст, не уникален (DATA-03);
- quarantine с номером физической строки начала записи: `bad_column_count`,
  `bad_date`, `bad_time`, `bad_bool`, `empty_channel`, `bad_encoding` (невалидные байты
  или NUL, экранируются в `import_quarantine.raw_cells`), `value_too_long` (> 4096
  символов). Повтор заголовка внутри файла — не запись (`technical_headers`), как в
  curated ETL. `quarantine_reasons` в сумме равны `rows_quarantined`.

**Запись журнала** — одна транзакция: `COPY` во временную таблицу, дедупликация и
`INSERT` в `dispatch_observations` канонического received-scope
(`INFRA_RECEIVED_NAMESPACE` / `INFRA_RECEIVED_STREAM_ID`), `availability_basis='observed'`,
`available_at` — время фиксации импорта после блокировки scope, плотный
`received_position`. Строки сразу видны в `/api/v1/attention` в режиме `received`.
Ключ перекрытия — (канал, время, `ид_события`, значение): `row_uid` =
`csv-<UTC-день>-<sha256 ключа>`; повтор внутри файла и уже принятые записи считаются
в `rows_duplicate`. Сбой посреди файла откатывает всё: ни строк, ни quarantine, ни
счётчиков; задание повторяется (до 3 попыток), затем `failed/internal_error`.

**Дубли по естественному ключу (29.09.2026, P0-1 репетиции).** Засев истории
(`scripts/seed_forecast_history.py`) хранит `row_uid` curated-снимка —
`sha256(source_sha256:record_ordinal)`, не `csv-…`. Поэтому уже сохранённая запись
ищется и по `row_uid`, и по самому ключу: тот же канал, `event_at`, `source_event_id`
(`IS NOT DISTINCT FROM`, пустой ИД — NULL) и `value_raw`. Совпадение — дубль, какой бы
`row_uid` ни был у сохранённой строки. Так же ищется запись с `alarm = NULL`, которой
файл дополняет признак тревожности. Поиск ограничен периодом файла (`event_at` от
первой до последней записи): для пачки планировщик выбирает пробы по индексу
`dispatch_observations_event_time_idx`, для суточного файла — hash anti join по
записям этих суток, а не по всей истории. Замер 29.09 на одноразовом PostgreSQL 17
(Docker, 500 000 синтетических строк истории, 11 500 каналов, стадия load, медиана
5 прогонов): новая пачка 5 000 — 0,190–0,205 с до правки и 0,178–0,181 с после; пачка
из 5 000 засеянных записей — 0,19–0,21 с и все 5 000 сохранялись второй раз, после —
0,062 с, 0 принято и 5 000 дублей; суточный файл 170 000 — 5,97–6,12 с и 6,04–6,12 с.
Тест — `test_seeded_history_under_another_row_uid_is_a_duplicate` (`make check-db`).

**Пачка из одних дублей не пересчитывает прогноз (P2-5).** Если загрузка ничего не
записала (0 новых строк, 0 дополненных признаков), а текущая публикация уже учла все
записи scope (`detector_position` ≥ `row_count`), время данных и действующий справочник
каналов, worker ставит `published` с текущим `forecast_generation` без пересчёта и
пишет в `notes` «Новых записей нет: прогноз не пересчитывался». Иначе, а также после
перезапуска worker между загрузкой и пересчётом — обычный пересчёт. Тест —
`test_file_of_stored_records_keeps_the_publication`.

**Справочники** (`ingestion/reference_csv.py`) версионируются по SHA:
`ref_versions` (`channels-<sha16>` и т.д.), строки — `ref_channels`, `ref_objects`,
`ref_states` дословно по номеру строки. Новая версия действует только для следующих
загрузок журнала: у прежних наблюдений остаются их `object_id` и `reference_version`.
Точный повтор строки — `rows_duplicate`; канал, записанный дважды с разным
содержимым, не сопоставляется (`reference_conflict`). Канал вне справочника
сохраняется с `object_id = NULL`, флагом `reference_unmatched` и учитывается в
`unknown_channels` (число различных каналов, DATA-04).

**Очередь и надёжность.** `jobs` в PostgreSQL: захват `FOR UPDATE SKIP LOCKED` под
транзакционной advisory-блокировкой, lease (`INFRA_WORKER_LEASE_SECONDS`, 300 с)
продлевается на каждом этапе. Задания идут строго в порядке загрузки. Каждый переход
статуса фиксируется, поэтому после рестарта (lease истёк) другой процесс продолжает
с последнего статуса. Воркер будится `LISTEN infra_import_jobs` или раз в
`INFRA_WORKER_POLL_SECONDS` (5 с); SIGTERM завершает его после текущего задания.
При старте воркер, подключённый владельцем схемы, применяет идемпотентные миграции
(`INFRA_WORKER_MIGRATIONS_DIR`, все файлы каталога, включая 0014 для audit). Под
рантайм-ролью `infra_pulse_app` (Compose и стенд) у него нет CREATE на схему, и он их
пропускает: миграции до его старта применяет сервис `migrate`
([миграция 9000](migrations/README.md#9000-рантайм-роль-api-и-worker)). Затем воркер
создаёт пустой received-scope. Запускается **один** экземпляр.

```sh
# Локально, INFRA_AUTH_MODE=dev_stub. PostgreSQL запущен; тот же DSN у API.
# Справочник каналов загружается первым.
export INFRA_DB_DSN='postgresql://USER@127.0.0.1:5432/infra_pulse'
INFRA_RECEIVED_STREAM_ID=local-received-1 uv run --locked python -m infra_pulse_backend.worker
INFRA_MODE=received INFRA_RECEIVED_STREAM_ID=local-received-1 \
  uv run --locked uvicorn infra_pulse_backend.api.app:app --host 127.0.0.1 --port 8000
curl -F format=reference_channels_csv -F file=@/path/справочник_каналов_датчиков.csv \
  http://127.0.0.1:8000/api/v1/imports
curl -F file=@/path/journal.csv http://127.0.0.1:8000/api/v1/imports
curl http://127.0.0.1:8000/api/v1/imports
```

### Поток через API и токены интеграции (B1x)

**Статус на 28.09.2026.**
- *Implemented:* путь «пачка JSON или XML → PostgreSQL → статус». XML — с 28.09
  (ТЗ §7 «JSON, XML»); ответы API — JSON.
- *С B2:* пачка, как и CSV, после загрузки пересчитывает и публикует прогноз
  (`published`).
- *Не проверено:* сервер и Docker.

Требования: DATA-06, DATA-02–DATA-04, API-04, SEC-03, частично ТЗ §7/§9/§10.
Инструкция для заказчика: формат, curl, лимиты, коды ответов, повтор —
[docs/INTEGRATION_API.md](../docs/INTEGRATION_API.md).

**Путь.** `POST /api/v1/observations` (`api/observations.py`) принимает
`ObservationBatch` из contract `imports.py` в JSON или XML.
1. `Content-Type`: `application/json` (и `application/*+json`) — JSON;
   `application/xml` или `text/xml` — XML; другой или без заголовка — 415
   `unsupported_media_type` (до проверки токена, как 413).
2. Тело читается с ограничением 5 MiB: по `Content-Length` сразу, иначе потоково.
   Превышение — 413 `batch_too_large`.
3. XML переводится в тот же словарь пачки (`ingestion/batch_xml.py`, `defusedxml`,
   `forbid_dtd`): корень `<batch>`, `batch_id` — атрибут или элемент, `<record>` с
   полями-элементами. DTD, сущности и внешние ссылки — 422 `xml_forbidden`, битый XML —
   422 `xml_invalid`, нарушение структуры — 422 `xml_structure` / `xml_duplicate_field`
   (не больше 100 ошибок, дальше разбор не идёт); больше 5 000 `<record>` — сразу
   `too_long` → 413. Разбор XML идёт в пуле потоков, не в цикле событий.
4. FastAPI проверяет схему (для XML — тот же словарь). Больше 5 000 записей — 413
   `too_many_records`, прочие ошибки — 422 с `record` (номер с 1).
5. Байты тела **как есть** пишутся в `INFRA_UPLOAD_DIR/<import_id>.json` или `.xml`;
   `file_name` — `observations-<batch_id>.json` или `.xml`.
6. Одна транзакция (`storage/integration_pg.register_batch`) пишет `import_files`
   (`journal_json`, `uploaded_by` = вызывающий), `jobs`, `observation_batches` и
   audit `observations.received` (в `details` — `container`: `json` или `xml`), затем
   делает `NOTIFY`. Ответ — 202.

Дальше работает тот же worker B1: ветка `journal_json` в `worker/runner.py`, разбор
в `ingestion/journal_json.py` (для `.xml` — тем же `batch_from_xml`, что в API),
загрузка через `load_journal`, пересчёт через `recompute`. В отчёте `source_layout` =
`api_batch`, `source_container` = `json` или `xml` (CHECK расширен миграцией 0021).
- Записи становятся теми же `JournalRow`, что строки CSV: общий `dedup_identity` и
  `row_uid`. Поэтому перекрытие с CSV, с другими пачками и с засеянной историей
  (по естественному ключу, [выше](#загрузка-csv-и-ingestion-worker-b1)) считается в `rows_duplicate`.
- `date` + `time` — МСК по правилу CSV; `event_at` разбирается тем же правилом, что
  в contract (pydantic `AwareDatetime`).
- `value` хранится дословно. Канал вне справочника сохраняется с `object_id = NULL`.
- Quarantine получает номер записи (`line_no`) и причину. Это то, чего схема не видит:
  `bad_date` (например, `2026-02-30`), `bad_time`, `bad_encoding` (NUL или одиночный
  суррогат), `value_too_long`. Остальные записи принимаются.

**Идемпотентность.** Ключ — `(client_id, batch_id)`, где `client_id` — вызывающий:
`integration:<имя>` или администратор.
- Тот же ключ и те же байты — 200 с сохранённым `ImportFile`, без новой записи и audit.
- Другие байты — 409 `batch_id_conflict`. Сравниваются байты тела, поэтому JSON и XML
  одной пачки — разные тела: повтор отправляется в том же формате, что первая попытка.
- Одновременные запросы с одним ключом: проигравший откатывается (`BatchRaced`),
  удаляет свою копию файла и отвечает как повтор.

Отличие от постановки пакета, где задан `UNIQUE (token_id, batch_id)`: здесь взят
`client_id`, чтобы повтор после замены токена с тем же именем оставался
идемпотентным. `token_id` тоже сохраняется в `observation_batches`.

**Токены** (`auth/tokens.py`, `storage/integration_pg.py`, миграция 0015).
- `Authorization: Bearer ipk_<43 символа>`. В БД только SHA-256.
- Поиск и отметка `last_used_at` делаются одним `UPDATE … RETURNING`, поэтому отзыв
  действует со следующего запроса. Сбой БД — 503 `auth_storage_unavailable`
  (fail closed).
- В `auth_deps.current_actor` bearer-ветка идёт первой в обоих режимах. Вызывающий
  получает `Me(subject_id="integration:<имя>", roles=["integration"], auth_source="token")`.
  CSRF к таким запросам не применяется: cookie нет.
- Неизвестный, отозванный или неверный по форме токен — 401 `invalid_token` с
  `WWW-Authenticate: Bearer`.
- Роль `integration` даёт только `ingest`. Группа каталога с таким именем ролью сессии
  не становится (`auth/ldap.py`).
- Лимит — `INFRA_INTEGRATION_REQUESTS_PER_MINUTE` (60) пачек в минуту на токен, для
  администратора — на пользователя. Окно скользящее, в памяти процесса. Проверка идёт
  до проверки схемы (XML к этому моменту уже разобран); превышение — 429 `rate_limited`
  с `Retry-After`.
- `GET /api/v1/observations/{id}`: интеграция видит только свои пачки, администратор —
  все; иначе 404 `batch_not_found`.

CLI администратора — `python -m infra_pulse_backend.admin` (DSN только из `INFRA_DB_DSN`):

```sh
uv run --locked python -m infra_pulse_backend.admin --actor <администратор> token create --name scada-ods-1
uv run --locked python -m infra_pulse_backend.admin token list [--all] [--json]
uv run --locked python -m infra_pulse_backend.admin token revoke tok-0123456789ab   # или --name
```

Каждое действие пишется в `audit_events`: `integration_token.created`, `.listed`,
`.revoked`, роль `admin`, автор `--actor` или `cli:<пользователь ОС>`. Токен
печатается один раз. Коды выхода: 0 — готово, 1 — ошибка БД, 2 — неверный ввод или
отзывать нечего. Выдача на сервере — [deploy/README](../deploy/README.md#токены-интеграции-и-поток-через-api-b1x).

### XLSX, журнал Приложения 1 ТЗ, audit запросов и «Исследование» (G1, 27.09.2026)

**Статус.** *Implemented* локально на одноразовом PostgreSQL 14 (`make check-db`) и на
локальном `received`-стенде (uvicorn + worker). Сервер, Docker и браузер не проверялись.
Требования: DATA-05 (XLSX), DATA-02 (текст без float), SEC-03 (журнал действий),
OPS-01 (локальный замер 20 пользователей); ТЗ §7, §9, §11, Приложение 1; матрица —
M3, M5, M6, M8 и риск «формат CSV Приложения 1» (внутренняя сверка с ТЗ 27.09).

**XLSX** (`ingestion/xlsx_source.py`). Тот же `POST /api/v1/imports`, те же `format`
(`journal_csv` и три справочника), воркер, карантин, дедупликация и идемпотентность по
SHA-256. Контейнер определяется по содержимому (ZIP-сигнатура `PK\x03\x04`), а не по
имени файла; `.xlsx` хранится под своим расширением. HTTP файл не разбирает. Воркер
читает **первый лист** `openpyxl` в режиме read-only построчно, только сохранённые
значения формул, без pandas. Ячейка становится тем же текстом, что в CSV:
- текстовая ячейка — дословно (`00017`, `1,5`, `01.01.1970 03:00:00`);
- целое число — без дробной части (`56682`, не `56682.0`), прочие числа — кратчайшая
  запись с точкой;
- логическое значение — `true`/`false`;
- дата без времени — `YYYY-MM-DD`, время — `HH:MM:SS[.ffffff]`;
- дата со временем — `DD.MM.YYYY HH:MM:SS`, как пишет источник: заглушка
  `01.01.1970 03:00:00` остаётся узнаваемой.

Формат отображения Excel не переносится. Значения, которые Excel сам изменил при
открытии CSV (`1,5` → 1.5), восстановить нельзя; для этого столбцы нужно держать
текстовыми. Пустые строки листа — не записи. Лишняя непустая ячейка справа —
`bad_column_count`, как в CSV. Лимиты: 50 MB файла (как CSV), 512 MB распакованного
архива и 1 млн строк листа. Превышение — `file_too_large`, ZIP без книги —
`unknown_format`.

**Журнал в формате Приложения 1 ТЗ** (`ingestion/journal_csv.py`, `LAYOUT_TZ`).
Второй допустимый заголовок: `ИД записи журнала, ИД канала данных, ИД типа канала данных,
Текущее значение, Дата записи`. Сравнение без учёта регистра, `_`/пробелов и `ё`;
разделитель CSV `,` или `;`; XLSX тоже. Правила — решение внутренней приёмки 27.09
(не представитель заказчика):
- **`alarm` = NULL, «не передан».** Колонки тревожности нет: признак не false и не
  выводится из текста. Столбец `dispatch_observations.alarm` стал nullable
  (миграция 0018), в contract `ObservedMessage.alarm: bool | None`. Читатели
  трактуют NULL как «не true»: счётчики и полоса исходных тревог берут только `true`,
  полоса «точный текст» — `alarm IS NOT TRUE` (`storage/attention_pg.py`), отчёты R1 и
  уведомления N1 — `alarm = true`. Детектор эпизодов фазы получает NULL как «не
  тревожное начало» (`start_alarm` — служебная пометка, не показывается).
- **Отчёт загрузки.** Новые поля `ImportFile`: `source_layout`
  (`organizers_export` | `tz_appendix1` | `api_batch` | `reference`), `source_container`
  (`csv` | `xlsx` | `json`), `alarm_not_provided` и `notes` — строки для администратора,
  например «Формат Приложения 1 ТЗ: признак тревожности источника не передан
  (N записей); время с точностью до минуты». Для XLSX добавляется «XLSX: прочитан первый
  лист книги». UI показывает `notes` как есть (F1, фронтенд).
- **Время.** «Дата записи» — одна ячейка `DD.MM.YYYY HH:MM[:SS[.ffffff]]` или ISO, МСК
  UTC+03:00; исходный текст — `event_local_raw`. Плохая дата — `bad_date`, нет или плохое
  время — `bad_time`.
- **Порядок записей.** Секунд нет, поэтому внутри минуты порядок приёма
  (`received_position`) задаётся по «ИД записи журнала»: числовые ID как числа.
  Детектор эпизодов (core) объединяет записи канала с одинаковым временем, поэтому сбой
  и восстановление в одну минуту склеиваются. Это ограничение формата. Экраны исходных
  сообщений сортируют по `available_at`/`row_uid`; перевод их на `received_position` —
  planned.
- **Тип канала** берётся из справочника каналов. «ИД типа канала данных» сохраняется
  дословно в `dispatch_observations.source_channel_type_id`. Если ID противоречит типу
  канала в справочнике, запись уходит в карантин `channel_type_conflict`. Соответствие
  ID таблицы ТЗ и названий типов справочника (`ingestion/channel_types.py`, например
  9 → «Состояние фазы», 12 → «Датчик температуры», 2 → КД/люки) — **предложение по
  названиям, требует подтверждения технолога**. ID вне таблицы, канал вне справочника
  или неоднозначный — не проверяются. Если в карантин ушли все записи —
  `no_valid_rows`.
- **Дубли между форматами.** Ключ совпадения тот же — (канал, время, ИД, значение).
  Заполненный `alarm` из выгрузки организаторов или пачки API заменяет NULL у уже
  принятой записи; счётчик `alarm_count` scope растёт, в `notes` — «Признак
  тревожности дополнен у ранее принятых записей: N». NULL никогда не затирает
  `true`/`false`. Уже посчитанное состояние детектора по такой записи не пересчитывается.

**Журнал действий пользователей** (ТЗ §11, SEC-03; `api/audit_log.py`,
`worker/runner.py`). Всё пишется в `audit_events` (0014, только добавление, триггер
запрещает UPDATE/DELETE) через `storage/audit_pg.record_audit_event`.
- **Доменные события — как раньше, в своей транзакции:** вход и выход
  (`auth.*`), решение и черновик, загрузка `import.uploaded`, пачка API и токены.
- **Смены статуса загрузки — воркер, той же транзакцией, что смена:**
  `import.status_changed`, актор `worker:<id>` без роли, `from`/`to` и счётчики отчёта.
  Сюда входят повтор после ошибки и истёкшая аренда.
- **Остальные запросы — ASGI-middleware:**

  | Маршрут | Что пишется |
  | --- | --- |
  | Просмотры: список и карточка прогноза, история решений, журнал и его сводка, качество, реестр, схемы, «Исследование», отчёт, список и отчёт загрузки, исходные сообщения и заметки | Строка на запрос: действие `forecast.card_viewed`, `scheme.viewed`, `research.viewed`… |

Отказы проверки, конфликта, лимита и недоступности там строк не оставляют: так спроектировали B1/B1x, их тесты считают только доменные строки |
  | Новый маршрут без правила | GET — `api.viewed`, запись — `api.called` |

  Окно сбрасывается первым запросом после его конца и при штатной остановке (lifespan).
  При аварийной остановке счётчики незакрытого окна теряются.
- **Состав строки:** актор, действующая роль (роль, давшая право; при отказе — пусто),
  шаблон маршрута, ID из пути, статус, исход (`success`/`denied`/`failure`),
  длительность, ключи и значения query (до 64 символов), `X-Request-ID` прокси.

  Запрос без опознанного актора (401, открытые маршруты) не пишется. Неудачный вход
  пишет `api/auth.py`.
- **Отказоустойчивость.** Строка пишется после отправки ответа. Если PostgreSQL
  недоступна, потеря пишется в лог `infra_pulse.audit`, запрос не падает. Без
  `INFRA_DB_DSN` (fixture, scaffold) middleware ничего не пишет. В `dev_stub` все

- **Чтение журнала.** API чтения и выгрузки журнала для администратора пока нет
