# Правила внесения изменений

Правила общие для всех участников, независимо от компонента.
Автор изменения отвечает за код, актуальные инструкции и доказательства проверки
в одном diff. Ревьюер проверяет их согласованность.

## Готовность задачи

1. Описаны изменённое поведение и границы результата: implemented, fixture или planned.
2. Выполнены применимые проверки; указаны команды, результат и непроверенные случаи.
3. Обновлены затронутые инструкции/контракты и проверены пути и ссылки.
4. При изменении готовности компонента или следующих шагов обновлён `docs/STATUS.md`.
5. Ограничения и блокеры названы явно. Неуспешная проверка не отмечена как пройденная.
6. Указаны применимые ID из [REQUIREMENTS_SPEC](docs/REQUIREMENTS_SPEC.md), ссылки
   на проверки и связанные [D/EX](docs/REQUIREMENTS_DECISIONS.md). При закрытии
   требования обновлены его статус/evidence; planned и fixture не становятся
   implemented без выполнения критерия. Для неприменимого изменения указана причина N/A.

Не требуется менять каждый документ для каждой правки. Если документация и статус
остаются верными, в описании PR/передачи достаточно указать, что обновление не требуется,
и кратко объяснить почему. Частичный результат передаётся как частичный, а не как готовая задача.

## Где обновляется информация

| Изменение | Документы и связанные файлы |
| --- | --- |
| Установка, публичные команды, архитектура компонентов | Корневой README; при деталях — docs/DEPENDENCIES.md, docs/ARCHITECTURE.md, docs/OPERATIONS.md |
| Backend/API, БД, миграции | backend/README.md; правила запуска/миграций в docs/OPERATIONS.md; статус реально доступных функций |
| Canonical contract | packages/core/src/infra_pulse_core/contracts; generated OpenAPI/fixture и frontend TS в том же diff; описание изменённой семантики |
| Frontend/UI | frontend/README.md при изменении запуска; docs/UI.md и docs/design/SYSTEM.md при изменении поведения/дизайна; результаты UI QA |
| Core: детектор и список прогноза | packages/core/README.md; версии, сверка с research (`check_core_parity_v9.py`); запуск/откат в docs/OPERATIONS.md |
| ETL, EDA, модели | data-science/README.md и инструкции соответствующего каталога; config/manifest/агрегированный отчёт; data-science/experiments/sensor-failure/README.md и DECISION_LOG при смене постановки |
| MLflow | data-science/mlflow/README.md; tracking/config/export и ограничения; локальный run не объявляется доступным всей команде |
| Инфраструктура, CI, зависимости | Соответствующие manifests/lock/CI/Compose; docs/DEPENDENCIES.md и docs/OPERATIONS.md; фактическая среда проверки |
| Новый или перемещённый документ | Ссылки из родительского README или docs/README.md; старые ссылки не должны ломаться |
| Требование, его допуск или открытое решение | docs/REQUIREMENTS_SPEC.md и docs/REQUIREMENTS_DECISIONS.md; затронутая компонентная спецификация; источник, версия и причина изменения |

README — устойчивое описание проекта для нового читателя, без имён участников,
обращений «ты/вы» и проектных прозвищ. Короткая датированная сводка этапа находится
в начале и ссылается на подробный статус. Списки персональных задач в репозиторий не входят.

`docs/STATUS.md` — текущая готовность, не дневник всех правок. В нём обновляется
соответствующая запись, а не добавляется противоречащая ей новая сводка.
Детальный журнал эксперимента/QA/review хранится в своей области и связывается ссылкой.
Существующие исторические метрики не переписываются под новый результат.

Нормы и критерии приёмки определяются в REQUIREMENTS_SPEC; подробные определения
данных/ML и механизмы — в профильной спецификации, на которую он ссылается.
В планах и статусе указывают requirement ID вместо независимой копии нормы.
README компонента ведёт к этим ID и описывает локальные команды. Если копии разошлись, исправляют основной источник
и ссылки на него; исторические review сохраняют прежние выводы с датой.

## Как фиксируется результат

В описании PR или передаче задачи достаточно следующего формата:

```text
Изменение: какое поведение/артефакт появился и для какого сценария.
Статус: implemented / fixture / planned; что осталось незавершённым.
Требования: ID → test/run/manifest/report; связанные D/EX или обоснованное N/A.
Проверки: команда → фактический результат; среда и существенные ограничения.
Документация: обновлённые файлы либо причина отсутствия изменений.
Следующий шаг: действие, входные данные/зависимость и ответственный, если применимо.
```

Для экспериментального результата дополнительно фиксируются версия кода (Git SHA
и dirty state), dataset/config/feature/target versions, контрольные суммы и команда
воспроизведения. Сырьё, приватные идентификаторы, модели, секреты и локальные БД
не попадают в PR. MLflow run ID без доступного tracking server не заменяет передаваемый
агрегированный отчёт и manifest. Notebook сохраняется без приватных outputs.

## Проверки

- Python: `make check`; при ML-изменениях — cutoff/leakage/censoring проверки.
- Изменение PostgreSQL read/write пути: `make check-db` с двумя
  `INFRA_TEST_*_DSN` на отдельную одноразовую БД. Пропущенные DB-тесты не
  считаются проверкой пути данных.
- Frontend: `npm --prefix frontend run build`; при изменении UI — применимая
  проверка сценария в браузере с указанием viewport/темы и результатов.
- Contracts: `make contracts`, затем `npm --prefix frontend run generate:api`,
  проверки совместимости и frontend build.
- Изменение запуска/инфраструктуры: соответствующий smoke/build; наличие файла
  Docker/CI не доказывает успешного запуска.
- Только документация: `git diff --check`, проверка внутренних ссылок и согласованности
  команд с существующими entry points. Если изменена сама команда запуска, проверяется
  её работа или явно указывается, что запуск не проверен. Полные кодовые тесты без
  изменения кода повторять не требуется.

Результаты прежнего запуска не выдаются за новый прогон. Ошибка, skip и блокировка
отличаются от успешной проверки. Достаточный scope проверки зависит от изменённого поведения.

Ревьюер проверяет трассировку requirement ID → критерий → evidence и обязательные
gates нормативной базы. Зелёный CI сам по себе не подтверждает SLA, модель или
полноту требований; автоматического requirements gate пока нет. Изменение смысла
требования и исключение проходят процедуру SPEC; открытый D блокирует только
зависимый этап. Датированное заключение не переписывают как будто исправление уже
существовало при первоначальной проверке.

## Совместная работа

Работа ведётся в отдельных ветках по одной задаче. Изменения общих контрактов и
зависимостей согласуются до параллельной правки. Документы обновляются вместе с
соответствующим кодом; конфликт статуса при слиянии разрешается по фактическому
состоянию объединённой ветки. Шаблон PR не запускает автоматический контроль:
проверка документации входит в review.
